# 长篇小说自动创作与连载服务：主方案

版本：Master Plan v1.0  
日期：2026-10-09（Asia/Shanghai）  
状态：需求与实施基线；不是已完成的生产服务。

## 一、产品目标

为个人作者提供一套可以持续运行的小说创作服务：

- 首先支持玄幻长篇连载，后续通过题材配置扩展悬疑、都市、科幻等。
- 支持用户提供自己的创意，也支持系统根据题材和偏好提出开书方案。
- 通过用户配置的 GPT / Gemini 等 API，自动完成世界观、人物、全书和分卷大纲、章节写作、审稿、返修、存稿。
- 在目标平台接入并验证后，管理投稿、排期、发布和结果核验。
- 第一阶段面向单个用户、多部作品；本地可运行，之后可以迁移到云端。

系统追求尽量自动。作者在开书约定中设置自动范围；锁定的事实、关系、正文片段和发布权限不能被模型自行解除。无法解决的阻断问题进入任务中心。

## 二、开书与自动连载流程

开书有两个入口：

1. 用户已有创意：输入人物、冲突或设定，系统提取明确要求，补全可选方案，并标出新增建议。
2. 用户没有完整创意：选择题材、风格、读者体验、篇幅和偏好，系统提出少量差异明显的开书方案，由用户选择。

两种入口进入同一流程：

创作约定 → 世界与人物 → 全书/分卷大纲 → 开篇场景 → 试写与文风校准 → 自动写作 → 审查返修 → 合格存稿 → 投稿与定时更新。

样章的文风认可和剧情采用分开记录。样章剧情只有正式采用后才进入故事事实。

作品可以设置单章字数、日更计划与时区、合格存稿目标、返修次数、调用预算、可自动修改范围、模型与文风版本、发布平台和失败策略。同一本书默认按采用后的章节顺序推进；不同作品可以并行。

## 三、页面结构

作品内导航收敛为六项：

| 页面 | 功能 |
| --- | --- |
| 概览 | 作品状态、采用进度、存稿量、当前卷、待处理问题、调用成本、试读反馈 |
| 创作 | 章节目录、候选稿、采用稿、正文编辑、差异、锁段、修改请求；侧栏显示本章依据、计划落实、审查和任务 |
| 设定 | 世界规则、人物、关系、人物弧光、群像分工、时间线、物品、义务与文风 |
| 大纲 | 全书、分卷、章节计划、前置条件、支线、伏笔、节点与正文落实情况 |
| 质量 | 硬冲突、语义疑点、信息不足、文风、节奏、群像、检查覆盖和变更影响 |
| 发布 | 投稿材料、平台绑定、存稿队列、排期、提交状态、核验、发布快照和历史 |

全局页面：

- 作品列表：多部作品、运行状态、存稿预警。
- 任务中心：后台任务、阶段、检查点、失败原因、重试、暂停和恢复。
- 系统设置：模型 API、模型角色、升级评测、密钥、平台连接、预算、备份与恢复。

## 四、每章生产闭环

1. 读取采用稿、当前有效故事状态、约束和章节计划。
2. 校验章节前置条件；缺失时补计划或暂停。
3. 生成 ContextManifest，记录实际使用的约束、人物、事实、原文、计划、伏笔和风格参考。
4. 资料分为作者硬约束、已发生事实、人物认知、未来计划、候选稿和参考材料。必需材料装不下时拆分、减少可选内容或阻断，不能静默截断。
5. 生成不可覆盖的候选稿。
6. 由模型提出 proposedChanges，独立抽取器从正文得到 observedChanges。
7. 比对事实、人物状态、物品、移动、关系、知识、义务、时间线和计划节点。
8. 执行确定性检查和语义检查。
9. 针对具体问题有限返修，检查范围、锁段、原稿版本和补丁重叠。
10. 检查通过后，在一个采用事务中提交正文版本、事件、状态和证据。
11. 用 outbox 任务更新摘要、检索索引、导出和统计。派生失败可重试，不重复采用正文。
12. 进入合格存稿；发布服务按排期创建快照，提交后核验平台结果。

候选稿和候选事件不能进入正式故事状态。只有采用稿产生正式事实。

## 五、人物、关系与群像

每个人物有稳定 ID，姓名、化名和称号映射到同一 ID。人物状态包括身份、目标、价值观、恐惧、底线、地点、伤势、能力、持有物、知识、误信、获知渠道、表达习惯、正文来源、故事时间和有效性。

关系拆成血缘身份、社会关系、单向信任与情绪、公开立场、私下意图、角色认知。关系可以锁定、允许发展，或在指定事件后变化。谎话和误认不能修改客观事实。

人物弧光记录：初始信念 → 触发事件 → 人物理解 → 关键选择 → 代价 → 后续表现。系统检查变化依据，不强迫正向成长。群像角色要有自己的目标、信息、利益和决定，出场数量不能替代角色分工检查。

玄幻增加 Obligation：誓约、承诺、交易、期限、触发条件、后果和证据。

## 六、结构、节奏与事实

剧情节点记录预期结果、前置事实、目标场景、正文证据、后续依赖、推进位置、收束位置和落实状态：未落实、部分落实、已落实、偏离、信息不足。邻章只读上下文不能算本章完成节点；大纲计划不能直接写入故事事实。

支线登记服务对象、推进节点、主题关联和收束条件。节奏检查篇幅消耗、信息变化、关系变化、局势变化、悬念兑现和剩余任务，允许铺垫和低强度章节。

故事账本记录故事时间、年龄、位置移动、物品流转、伤势恢复、能力变化、信息获取、伏笔、承诺和期限。确定事实用程序检查，模糊旅行和超自然规则结合世界设定审查。

## 七、版本和状态不变量

必须区分候选稿、采用稿、合格存稿、发布快照。关键对象包括 ContextManifest、PlanRealization、StateProvenance、Obligation、ChangeSet、CheckExecution、ProjectionTask、EditLock、ModelConfigVersion。

核心不变量：

1. 候选事件不污染状态。
2. 锁定关系和锁段不能被生成覆盖。
3. 计划不冒充事实，未来弧光不提前进入当前状态。
4. 事实关联正文版本、证据位置和故事时间。
5. 早章修改使相关后文、状态投影和检查结果失效。
6. stale 历史版本只能审计，不能进入续写上下文。
7. 重叠补丁报告冲突，不能覆盖。
8. 必需检查只有 passed 才能采用；failed、inconclusive、unavailable 都阻断。
9. 采用成功和摘要/索引成功分开显示。
10. 任务恢复不能重复采用或未经核验地重复发布。
11. 同书章节串行，不同书受控并行。
12. 当前有效版本和最新历史版本分开表达。

## 八、投稿、发布与安全

平台使用独立适配器，逐个平台核验创建作品、投稿、章节发布、结果查询、编辑和撤回能力。发布状态为 scheduled → submitting → verifying → published；超时进入 unknown，先查询再重试。首发、更新和修订使用不同发布意图。

首个平台未确定前，不承诺自动投稿。平台规则、AI 披露、字数、版权、审核和相似度要求逐平台确认。

第一版还需具备 API Key 加密和脱敏、最小权限、费用预算、限流、重试上限、作品隔离、导入提示注入隔离、导出备份恢复、删除、审计日志、内容审核、自动发布开关和紧急暂停。相似度检查只能提示人工核查，不能保证法律意义上的绝对原创。

## 九、技术架构与实施阶段

推荐 TypeScript 模块化单体加独立 worker：

apps/web：React + Vite + TypeScript  
apps/api：NestJS / HTTP + SSE  
apps/worker：Node.js 调度、执行和恢复  
packages/core：作品、设定、人物、大纲、状态、写作、质量、发布  
packages/persistence：PostgreSQL + Prisma + migrations  
packages/model-gateway：GPT/Gemini 适配、路由、预算、重试和用量  
packages/platform-adapters：平台实现  
packages/contracts：Zod / JSON Schema  
infra：Docker Compose、备份与迁移

数据库是业务状态依据，Redis只作为队列协调。采用使用事务与 outbox；检索索引是可重建派生数据。

实施阶段：

0. 确定平台、部署、读者、字数、日更、文风、模型分工和自动发布授权。
1. 作品、配置、模型网关、密钥、版本、数据库、worker、预算、日志和备份。
2. 开书 A/B、玄幻配置、世界人物、大纲、候选章节、检查、采用、状态和存稿。
3. 样章校准、精确编辑、差异、锁段、上下文清单和节点落实。
4. 人物弧光、群像、关系、时间空间、物品、义务、变更影响和声明互核。
5. 连续写 10～20 章，验证暂停、重启、费用、失败、早章修改和跨卷依赖。
6. 用平台替身验证投稿意图、快照、超时核验和幂等，再接入真实平台。
7. 扩展题材、平台、反馈指标和可视化，多用户商业化暂不进入第一阶段。

## 十、已验证与未验证

novel-service-spike 已通过 Python 5 项测试和 Node 3 项测试：12 章连续采用、候选隔离、检查器不可用阻断、早章影响、checkpoint 恢复、租约恢复、幂等采用、同书串行、跨书并行和任务去重。

Spike 使用假模型、Python 内存聚合和 Node JSON 文件。它验证状态边界，尚未验证真实模型质量、PostgreSQL 并发、Redis、网页界面、云部署或平台发布。
