# 可恢复的分批设计评审

世界、力量、人物和故事四项仍独立评审，结论绑定完整设计与所选计划版本。评审不会批准计划、锁定设计、写正文或采纳事件。

计划范围分两层：`plan/overview.targetChapterCount`保留全书或本次里程碑规模，`detailedThroughChapter`表示从第1章开始连续具备细纲的终点，`outlinedChapterNumbers`列出所有已展开章号（包括连续范围以外的章纲）。例如目标100章、目前细纲1–50章时，前50章须核对场景可执行性，后半本检查宏观因果、成长前置、选择代价和收束。不能仅因后半本尚未写逐场招式或逐日训练就要求一次性展开；也不能用分阶段规划掩盖已经存在的矛盾。新增细纲会改变评审指纹，必须重评，旧通过不能覆盖新范围。

## 原文与结论

- 原材料序列化后不超过 240,000 字符：一次原文评审，保留原来源 ID。
- 超过容量：按最多 10,000 个 UTF-16 字符切片（不切开代理对），保留来源 ID 和起止范围；每批普通原文序列化后不超过 100,000 字符，另可携带以下公共原文。
- 公共原文调度（`scheduleVersion: 2`起）为每个原文批次和跨批检查重复携带最多40,000字符的公共原文。力量优先带全书范围、公理、境界、品阶、功法和法宝；人物优先带范围、角色起点和世界规则；世界与故事优先带范围、规则和地点。每个公共来源完整选取，超过公共容量的条目仍完整进入普通批次，不截断或总结。单次最多是两批各100,000字符加一份公共原文，公共来源在同次请求内去重。
- 每个原文批次独立评审，再对每一对批次共同读取原文，检查跨批矛盾。最后用二叉树综合全部原文和跨批报告。新版调度3为综合阶段额外附上完整的 `plan/overview` 原文（最多40,000字符，过大则仍保留在普通原文批次），避免将前置报告对详细章纲范围的误读继续传播。单次来源仍受 240,000 字符上限约束，不截断原文或模型结论。
- 原文批次数为 n 时，原文与跨批评审共 n(n+1)/2 次，加上综合共 n(n+1)−1 步。调度5如安排 f 个专门补读，连同新增综合步骤，总计 n(n+1)−1+2f 步；原始检查结束前显示的总数可能增加。最多 64 个原文批次；这是上限而非建议规模，较大材料的调用量和费用会显著增加。
- 旧调度每个结果最多40,000字符。调度3按实际发送给综合步骤的完整JSON来源封装限90,000字符（包括引文、转义和缩进），两份报告加最多40,000字符计划原文仍低于240,000字符输入上限；失败与模型原答单独保存，不作为报告重新喂给综合。证据必须精确匹配本次输入。综合须区分 `review-result/` 前置报告与附带的计划原文，不把报告转述冒充故事事实；前置报告及原始证据始终保存在批次记录中。
- 最终提交重新核验切片范围、完整调度、所有阶段的证据，并保留每项标准最严重的判定。唯一可解决的局部等待是下文规定的显式补读，普通材料不足与返修仍不能被综合模型改成通过。

覆盖校验只能证明材料确实被安排送审，不保证模型理解无误。局部通过、全量步骤完成、设计通过、批准计划与正文验收是不同状态。模型意见需要结合原文核对；仍需人工修订和重新评审。

## 执行与恢复

`POST /works/:workId/design/review-runs` 创建或恢复同版本同领域的未完成任务；请求体为 `{area, planId?}`。不调用模型。

`POST /works/:workId/design/review-runs/:runId/step` 只执行一个步骤。每步保存结果、尝试次数、失败历史和模型原答。前端循环推进，可选择“本批后停止”；刷新或服务重启后“继续本项”从未完成处恢复。已有步骤不重复调用。

`GET /works/:workId/design/content-reviews` 返回版本、结论和进度摘要。`GET /works/:workId/design/review-runs/:runId/stages/:stageId` 查看该批输入和记录；综合阶段需前置批次完成才能构造输入。`stageId` 作为一个路径段编码，例如 `followup-batch-3%2Frelationships`，不能将编号里的斜杠当作路由分隔符。

模型请求在数据库事务外执行，以带心跳的租约和令牌防止并发覆盖。失联进程租约到期后可以重试；旧进程无法覆盖新结果。设计改动后旧任务不能继续，必须重新开始。新一轮未完成评审会挡住旧的通过结论。旧同步评审接口兼容保留，但浏览器采用逐步接口。

没有`scheduleVersion`字段或版本2的旧任务仍按原调度恢复、校验和结束，不重排已经评过的材料。公共原文只影响新建任务；继续旧任务不会补加上下文，也不能把其“本批缺材料”结论自动改为通过。新调度减少章纲与基础规则被拆开的误判，但40,000字符不能覆盖所有依赖，仍须核对模型是否误把局部未见当成全书缺失。

## SQLite 升级

停止 API 后，在仓库根目录执行：

```sh
python3 scripts/migrate-design-review-runs.py data/novel-studio.db
npm run generate -w novel-studio-persistence
npm run dev:api
```

迁移使用 SQLite backup API 在同目录的 `audit-backups` 保存备份，再向 Project 新增 `designReviewRuns TEXT NOT NULL DEFAULT '[]'`。重复执行不修改已有字段；不重置数据库或改写计划、正文、事件。原有 JSON 仓库缺少此字段时按空数组加载。

PostgreSQL 部署需在自己的迁移流程中添加 `"designReviewRuns" JSONB NOT NULL DEFAULT '[]'::jsonb`，再按 PostgreSQL schema 生成客户端；本次恢复验证覆盖 JSON 与 SQLite，未在 PostgreSQL 实例上实测。

评审指纹版本已升级，旧报告仍保留，但须用新流程重评后才能再次作为当前设计的放行证据。

## 请求绑定与短证据编号

模型响应在顶层回传本次 `requestId`，证据选择使用请求内唯一的 `e1`、`e2` 等短编号。请求指纹绑定完整材料、来源身份、范围与版本；即使另一请求也有 `e1`，旧请求编号仍会拒绝。解析后存储的报告保持真实 `sourceId` 与连续原文，不把短编号当长期证据ID。错误只允许同模型显式修正一次；不会模糊匹配、补编号或自动换引文。已有阶段与旧报告仍保留，续跑的新阶段使用新传输格式。

## 明确局部范围和跨批补读（调度3）

调度3普通原文批次最多90,000字符，公共原文仍最多40,000字符；两个原文批次与公共原文合计最多220,000字符，为显式补读问题预留20,000字符，不截断原文。新任务每步带 `stage.coverage`。`sourceLengths` 是完整输入的来源ID与字符长度目录（目录与补读元数据合计最多40,000字符，超限报错，不截断）；结合既有 `sourceMap` 区分本次完整读取、只读一段及位于其他批次的来源。目录不能作为引文，不能证明内容正确。`whole_input`、`local_sources`、`reports_with_context` 区分整项原文、局部原文与报告综合；原文及问题来源仍受每步240,000字符容量限制。

局部 `insufficient` 可额外返回 `awaitingSources`，指定1–64个确实存在于目录、但本次尚未完整提供的来源。缺规则、原文内部矛盾、整个输入确无来源不能使用此字段；`revise`不能标成等待。旧报告里没有此字段的材料不足不自动改分类。

后续原文步骤只有同时覆盖原批全部字符片段和所有请求来源的完整原文，才会收到 `pendingChecks` 与 `review-question/` 原问题。若添加问题超出原文容量，不丢弃原文来挤进问题，也不授权本步解除等待。模型需要逐项明确输出 `resolves`，同一标准须为pass，并引用原问题、原批实际材料及每个补读来源至少一段。仅仅在别处给了pass、只看目录、只看部分所需原文、没有引用补读证据或只由综合模型宣称解决，均不能解除等待。

最终聚合重验每步，并输出 `resolvedDeferrals` 对应原等待项和复核步骤；原始insufficient、原答、引用和复核记录都保留。真实revise、普通insufficient和未解决等待仍阻断。如果关联跨越多批且没有一个原文步骤完整覆盖请求，保留材料不足，不把分别读过当作联合核验。当前不会自动追加无界补读或额外模型调用。

综合阶段收到已校验的补读处理记录和计划原文，避免重新传播已明确处理的局部等待；综合本身不能输出补读处置。界面在批次详情展示等待来源、解决项和最终处理记录。此机制改善证据追踪，不能证明模型对文学质量、因果或人物动机的理解一定正确。

## 章纲配对与专门补读（调度4、5）

调度4尽量将同一章的圣经概要与计划细纲一起送审，避免把概要省略的成本误判为整份设计缺失；过大来源仍切片，既有容量上限不变。

调度5及以后的任务在原始批次和跨批检查全部完成后，为尚未解决且明确列出 `awaitingSources` 的问题安排一次专门补读，然后重建综合树。优先补齐原批、引用来源及请求来源；超过容量时，仅保留原问题所引用来源的完整原文、每个请求来源、完整共享规则及计划范围。无引用依据或完整原文仍超出240,000字符时不缩短来源，保留不足。

专门补读只审原问题的标准，解除须显式返回 `resolves`，并引用原问题、每个原始依据及每个请求来源。材料齐备不自动等于通过；普通不足和实质返修继续阻断。补读不再递归建立等待，单个原等待最多新增一次模型步骤。为容纳联合来源的证据，单项引用上限为64，报告封装容量不变。

补读计划由原始材料及已验证原始结果派生，保存和恢复后保持一致；最终重新构造并校验完整调度。已有调度1—4任务不插入新步骤，按原计划恢复和结束；不能把新流程的离线验证结论填进旧正式报告。

## 综合报告引用边界（调度6）

调度6起，原文切片与补读调度不变。供综合评审读取的报告将每段证据作为独立摘录展开，标出来源、切片编号和能唯一确定的原始UTF-16字符范围；解释、判定、等待和解除记录全部保留。非连续摘录不能拼成同一个人物阶段、物品条目或时间事件。重复文本不能唯一定位时只标记位置不唯一，不冒认首个匹配位置。

证据仍须精确匹配本次输入，原始结果不改写；240,000字符输入、90,000字符报告封装及最终完整调度校验继续生效。渲染前置报告时缓存已展开的报告，避免深层综合反复展开同一段历史。已有调度1—5任务继续使用原JSON报告格式，不在恢复中替换已评材料。新格式帮助避免把相隔的片段误拼成冲突，并不保证模型理解正确，也不自动删除旧返修或解除阻塞。

## 局部检查与最终标准（调度7）

调度7起，只有未覆盖全量原文的普通batch/cross步骤，才将标准明确限定为本批实际材料：检查局部行动与直接前置、具体日程、实际伏笔兑现、可比较的冲突递进。不能要求每个局部批次独自证明前五十章或整个领域完整成立。内置故事标准按这四个具体问题表述；其他领域和自定义标准保留原始要求并加局部范围说明。

局部pass仅表示实际已读范围成立。发现本批自身缺规则、真实矛盾、无来源支出仍须返修；确实依赖某个未读来源时须明确具体事实和完整所需来源，继续使用可审计的等待与补读机制。不能把“本批有13章而非50章”单独当作缺料，也不能借局部范围跳过已知依赖。

力量领域还须核验本批完整提供的所有等级规则本身，包括尚未在章纲使用的高阶能力；共享境界、功法和资源不是只读背景，不能只核当前低阶行动账而漏掉原规则的真实缺口。

完整输入、专门补读及综合步骤仍使用原标准。任务自身的全领域rubric、全部原文、切片、跨批覆盖、引用校验、最严重判定保留和最终调度重建没有缩减。旧调度1—6恢复时保持其原始输入；正在运行的调度5不会被改写成局部通过。

## 宏观计划、执行细纲与来源范围（调度8、9）

调度8明确区分摘要和细纲：宏观摘要没列动作费用时，先核对应的现存细纲，不能据摘要省略断言整个设计没有支付；原规则自身缺陷仍须返修。

调度9引入`coverage.planRanges`，从本领域现有`plan/volumes/`和`plan/milestones/`原文提取章号范围及标题，方便定位尚未读到的宏观依据。例如第61–66章尚无细纲，但目录可指向覆盖该区间的北港救援里程碑，按其实际交通、准入、资源和行动前置核验。无法解析或无合法章号范围的来源不推测范围，原来源仍完整保留在来源目录与原文批次中。

该目录仅供查找，不能用作证据、认定剧情已发生或自动判通过。旧版世界领域只纳入宏观计划，不能把旧任务目录没有逐章来源误报成作品不存在这些细纲；当前新建输入的范围见下节。需要尚未读取的现有宏观依据时，仍须通过`awaitingSources`请求实际来源；读到后缺关键因果、预算或准入，仍保留不足或返修。目录与其他覆盖元数据共同受40,000字符上限约束，超限明确报错而不截断。

调度9不改变源文、切片、配对、跨批覆盖和补读解除要求，也不将旧的普通材料不足改为可自动解除的等待。调度1—8的恢复输入保持原样；正在执行的正式55不切换调度、不注入离线试验结果。

地理标准还须核验计划的实际动作，不能仅复述世界规则和航程摘要：逐项对照起讫地点、交通方式、操作者资格、准入依据与支付供能。正确的票款和总天数不能证明中间的移动方式合法；局部担保也不能自动扩大为别处的准入权。此标准升级使用评审指纹9，旧指纹7、8的报告继续保存，但不能作为新版设计放行依据。运行中的旧进程仍按已载入的规则完成；升级服务后须重新评审。

## 完整世界输入与实体名称导航（指纹12、调度10）

指纹12、调度10加入以下能力。世界领域也完整纳入故事圣经章概要与所有现存计划细纲，便于核对实际交通、防护、准入和支付；不会因为世界领域缺少逐章输入而反复要求作者补写已有内容。尚未展开的后段仍按宏观计划核验，不要求一次生成数百章细纲。来源范围变化已绑定新指纹，旧报告不能充当新输入的通过证据。

调度10在`coverage.sourceNames`中提供世界实体和人物的原始名称或标题，帮助模型区分相似条目，例如护身符佩与赤霞斩铁剑。名称仅用于定位原文，不能引用目录作为证据，也不能凭名称判断品阶、效果或成本。模型仍须读取正确来源；全部原文、证据匹配、补读解除和最严重判定保留要求不变。名称目录与其他覆盖元数据合计仍受40,000字符上限约束。

已有调度1—9任务继续使用原保存输入和原调度，不注入名称、不补加细纲、不改写已完成阶段。冻结旧运行器不会因仓库代码升级而自动采用新版本；恢复时须保持其原运行环境，待任务结束后再升级服务和建立新评审。

## 中间汇总与最终汇总（指纹13、调度11）

指纹13、调度11开始为每个综合步骤计算`coverage.synthesis`：`coveredStageIds`列出真实依赖树中该子树涵盖的原文、跨批及补读步骤，`totalStages`是这些步骤的全领域总数。未合并所有步骤时标记`partial_reports`，最终完整子树才标记`complete_reports`；增加补读后按实际重建的树计算，不使用固定初始步数。

中间汇总仍逐项使用原rubric，检查本子树报告的依据和相互冲突。它不需要独自证明其他子树尚未合入的全部后半段伏笔或前五十章场景；不能仅因报告树尚未汇齐就新增全领域材料不足。最终汇总保留完整标准，检查所有分支的结论与关联。该范围信息仅说明报告覆盖，不说明任何故事规则成立，不可充当引文，也不把覆盖完整当成设计通过。

原文、跨批配对、补读请求及明确解除条件保持原样；原报告中的真实返修、普通不足、未解决等待和中间汇总新发现的冲突继续参与最终最严重判定。即使最终模型给出pass，系统也不删除这些未通过项。旧调度1—10不增加该字段，保存后恢复的范围保持原样。正在运行的冻结正式56仍按指纹10／调度9完成，本次改动不改写它的输入或结果。

## 将补读处理说明放回对应问题旁（指纹14、调度12）
