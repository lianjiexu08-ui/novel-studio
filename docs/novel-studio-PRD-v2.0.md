## 阅读与执行说明

本文规定“产品应该怎样工作”；配套的 `novel-studio-DEVELOPMENT-BACKLOG-v2.0.md` 规定“按什么顺序修改代码、怎样验收”。先完成 P0 的作者逐章确认闭环，再开启 P1 的有限自动推进。不要为了完成本文而推倒现有候选稿、事件账本、版本、仓储和 outbox 体系。

本轮确定的方向是：全书和分卷提前规划；前 50 章有逐章内容；高潮有前置铺垫；正文逐章生成、评审、修改和采用；作者可以评论正文，也可以简单记录或与 AI 讨论后续期望。文中的数字默认值可配置，变更影响由后端判断，不依靠页面按钮约束。

## 01. 产品定位与成功目标

### 1.1 产品定位

帮助中文玄幻、仙侠长篇作者规划故事、写出可用章节、检查长期一致性，并通过评论和讨论逐步完善自己的作品。第一阶段面向单个作者、多部作品、本地优先；保留现有技术栈。多租户商业平台不属于本轮范围。

核心价值不是生成字数，而是降低作者在构思、核查和返工上的负担。作者拥有设定、剧情、采用和发布的决定权；AI 提供整理、建议、生成、抽取与评审。

### 1.2 核心验收目标

完成“已批准全书规划与前 50 章章纲 → 真实模型逐章写作 → 作者评论 → 局部返修 → 复查 → 作者采用 → 下一章”的闭环。先以连续 10 章验证可用性，再以 20 章和一卷验证长期衔接。生成了 100 章不等于完成质量验收。

记录每千字采用稿的作者操作时间、总模型成本、采用后结构性返工、严重一致性问题与误报、持续写作次数。第一版收集基线，不虚设已有数据或承诺某个提升比例。

### 1.3 不做什么

本轮不做一键无人值守生成数百章、自动发布、爆款概率预测、公开读者社区、多人实时协同、复杂商业计费、全题材覆盖、封面视频生产。允许普通修辞与合理想象；需要阻断的是与已确立内容冲突、无依据的关键状态变化、作者明确禁止的内容和无法解释的因果跳跃，不是禁止一切新增细节。

## 02. 关键产品决策

| 决策 | 本版规则 |
| --- | --- |
| 全书目标与生产目标 | 分开记录。全书可以规划 450 章，本轮只写 1 章；100 章是阶段里程碑，不自动代表完结。 |
| 规划粒度 | 全书方向明确；所有分卷有任务；前 `min(50, 全书目标)` 章有逐章章纲；近期 5—10 章重点校准；当前章细化到场景。 |
| 写作方式 | P0 默认逐章生成、评审、作者采用。下一章必须基于前面连续有效的已采用正文。 |
| 评论与讨论 | 评论可修改当前正文；未来期望可形成计划提案。提问、讨论、草案都不自动执行。 |
| 采用权 | 默认仅作者。P1 有限自动模式必须按次明确授权范围、预算和停止条件。 |
| 计划与事实 | 计划不会自动成为正文事实；角色误信不会改写客观事实；作者讨论也不是角色已知信息。 |
| 锁定 | 当前批准版本不可被模型覆盖；作者可批准新版本。锁定文档不等于所有角色关系永远不能发展。 |
| 修订 | AI 与作者改动都先生成新候选；比较差异、复查后采用。旧版本可读，不原地覆盖。 |
| 成稿 | 任意连续有效章节可冻结阶段快照；只有最终完结检查才要求全书范围的必要收束。 |
| 模型未配置 | 只能明确进入隔离的演示模式；演示稿不能进入正式作品采用、自动运行或正式书稿。 |

建议默认值：单章目标 2200 字；自动返修上限 2 轮；阶段复盘每 5 章；详细章纲窗口 50 章；近期校准窗口 10 章；P1 自动推进默认最多 3 章、首版上限 5 章。它们是可配置的产品初始值，不是叙事质量定律。

## 03. 端到端流程

### 3.1 新书

```text
记录作者意图或选择故事方案
  → 核心冲突、人物与必要世界规则
  → 审核并批准世界与故事基础
  → 全书总纲和分卷计划
  → 前 50 章章纲与高潮前置条件
  → 审核并批准计划
  → 样章校准（可选；风格认可不等于剧情采用）
  → 准备当前章任务卡
  → 检查前置条件并组装上下文
  → 生成不可变候选稿
  → 独立抽取、事实检查、叙事评审
  → 作者阅读、评论、讨论或要求修改
  → 新候选稿与差异预览 → 重新检查
  → 作者采用 → 提交正文、事件、检查点和 outbox
  → 下一章；到达阶段边界先复盘
```

### 3.2 读后修改

```text
整章评论或选段批注
  → AI 判断是提问、建议、明确修改还是未来期望
  → 需要时与作者讨论
  → 形成有范围、有保留项的修改提案
  → 生成修订候选，不覆盖原文
  → 差异预览和重新抽取／评审
  → 作者采用新版本 → 评论等待验收／作者关闭
```

涉及已采用早章时，先计算后文影响；作者确认切换修订版本后，保守标记后文待复核并停用受影响事实。尚未切换时旧正式链仍保持有效。

### 3.3 后续剧情讨论

```text
作者随手记录想法
  → 在指定作品、章节或剧情节点下讨论
  → 区分作者原话、已确认要求、AI 建议、待决问题
  → 整理成剧情提案
  → 展示影响的章纲、人物弧光、伏笔和前置条件
  → 作者批准 → 生成并激活新计划版本
  → 未采用且依赖旧计划的候选变为过期
  → 后续生成使用新计划，已采用事实不自动改写
```

## 04. 信息分层与统一设定来源

### 4.1 五种信息不得混用

| 层 | 含义 | 例子 | 正式生效方式 |
| --- | --- | --- | --- |
| 作者约定 | 给谁看、必须保留、禁写内容、文风偏好 | 前 50 章主角不依靠碾压战力获胜 | 作者确认约定或约定修订 |
| 客观设定与事实 | 世界底层规则、经确认的开篇基线、已采用正文事件 | 禁术损伤寿命；账册在第 12 章被替换 | 设定批准或正文采用；来源必须区分 |
| 人物认知 | 某角色知道、误信或不知道什么 | 主角仍认为账册是真的 | 基线声明或有证据的认知事件 |
| 未来计划 | 未发生的剧情与人物发展 | 第 23 章主角发现替换行为 | 计划批准，仅供规划使用 |
| 讨论与候选 | 作者草记、AI 建议、未采用正文 | 可以考虑让证人隐瞒身份 | 不具有事实权威 |

P1 可进一步区分读者已知信息、叙述者知识和公开／私下信息。P0 至少严格区分事实、人物认知和未来计划，不用一个自由文本字段混装。

### 4.2 手填设定与生成设定

保留作者手填能力，采用统一实体 ID、别名与来源。Story Bible、世界包、手填人物页可以是不同视图与聚合，但不能形成相互隔离的权威人物库。合并时显示差异与冲突，不能让最后写入的一方静默覆盖另一方。

每个实体至少记录 `entityId`、类型、别名、来源、版本、状态、适用范围和锁策略。手填设置可以被明确纳入指定计划版本，不因“出现在设定页”就自动成为 Story Bible 的未来剧情。

### 4.3 锁策略

区分 `document_revision_locked`（已批准文档版本不可改写）、`baseline_locked`（初始定义不可擅改）、`event_change_forbidden`（这个事实或关系禁止被故事事件改变）、`evolvable`（可以通过符合条件的事件发展）。

例如，人物血缘关系可以禁止变动；人物互不信任只是开篇基线时，可以在有依据的事件后变化。旧 `locked=true` 迁移时按原来禁止事件改写的语义保守保留，不自动放宽。模型只能建议变更，不能解除锁定。

## 05. 开书与创作约定需求

**OPEN-01｜P0｜开书立项卡。** 支持书名、题材、目标读者、核心吸引点、主角目标、主要阻碍、期待的阅读体验、必须保留、禁止内容、单章字数、全书目标章数与卷数。后端检查读者、吸引点、目标篇幅等必填项；不能仅依赖前端 `covenantReady`。

**OPEN-02｜P0｜两种输入。** 作者可输入完整构思，也可只写一句话，由 AI 提出 2—3 个主线或代价确实不同的方案；作者选定后才写入立项卡。无需填写大量世界细节才允许开始构思。

**OPEN-03｜P0｜意图来源。** 作者原话不可变留存，AI 补充单独显示；批准时记录作者接受的具体内容。未经确认的建议不进入硬约束。

**OPEN-04｜P0｜版本和变更预览。** 修改约定生成新版本；显示哪些计划与候选需要复核。P0 可保守使全部未采用候选过期，但不能把已有正式正文自动重写。

**OPEN-05｜P1｜样章文风校准。** 支持少量同剧情不同表达的样章，作者选择并形成文风卡。风格认可与剧情采用是两个动作；样章只有完成正式检查与采用才产生事件。

## 06. 分层规划与前 50 章需求

**PLAN-01｜P0｜全书计划。** 记录主线冲突、主题方向、主角最终变化、结局方向、目标章数、卷数和关键转折。若作者未决定结局细节，可记录结局方向与待决项，但不得留下阻断开篇的未决问题。

**PLAN-02｜P0｜分卷安排。** 每卷记录序号、起止章、章数、卷目标、主要对手或阻力、主要人物、高潮节点、结束状态和接续问题。章节范围连续不重叠，章数之和等于当前全书计划目标；数字是可修订计划，不是强制注水。

**PLAN-03｜P0｜逐章章纲。** 正式写第一章前，完成并批准前 `min(50, targetChapterCount)` 章章纲。每章有事件摘要、人物目标、主要冲突、关键选择、代价或后果、推进的线索、结束状态；不是只填章节名。允许系统按 5—10 章分组生成，再整体校验衔接。

**PLAN-04｜P0｜当章任务卡。** 基于已批准章纲与当前事实整理视角、出场角色、地点、故事时间、场景序列、必须完成事项、禁止提前发生事项、结束状态、依赖事实和不应改动内容。作者可简单修改；未出现重大改变时可直接沿用批准章纲的授权，不重复强迫作者填写。

**PLAN-05｜P0｜高潮与前置条件。** 每个高潮记录章节范围而非必须精确单章；列明铺垫、资源、人物知识、选择、代价、兑现线索和结束后的局势。支持 `must` 与 `optional` 依赖；关键前置未满足时阻断相应章任务，不能临时创造能力来补漏洞。

**PLAN-06｜P0｜计划审核。** 执行引用闭合、章数与区间、循环依赖、阻断未决项检查，并给出主线推进、动机、代价、铺垫与兑现的语义建议。结构检查通过不自动代表文学质量优秀；正式计划仍需作者批准。全书细纲不要求一次性全部展开。

**PLAN-07｜P0｜计划修订与滚动展开。** 支持修订未写章纲、扩展后续窗口、改变目标章数和追加卷。扩展输入包括当前事实快照、已实现节点、旧计划和作者要求；保留已采用正文与已发生事实。前 100 章只看旧蓝图、不看实际正文的扩展不合格。

**PLAN-08｜P1｜自动阶段复盘。** 默认每 5 章触发短复盘，每卷结束触发卷复盘；近期 10 章校准，第 40 章附近提示扩展第 51—100 章。输出偏离、重复、缺少铺垫和逾期待兑现事项；只提出修订，不能为给偏航开脱而自动修改计划。

**PLAN-09｜P0｜计划落实。** 计划节点区分 `unrealized / partial / realized / diverged / insufficient`，依据当前有效正文证据展示。`diverged` 不自动当作完成，必要的主线偏离需要作者批准新安排。未到期伏笔不按漏收束处理。

### 前 50 章规划的最低内容示例

第 1—5 章建立目标与困境；第 6—15 章取得第一份证据并暴露行踪；第 16—25 章发现证据误导、改变方向；第 26—35 章取得局部胜利且付出代价；第 36—44 章旧计划失效；第 45—50 章兑现本卷承诺并处理后果。此例是演示，不是固定模板，不要求所有题材照抄同一节奏。

具体章纲示例：第 12 章，主角牺牲一部分资源换到账册残页，发现运输记录矛盾；同伴因此怀疑其身份；本章只建立疑点，不揭露幕后真凶。预期变化与实际变化分别保存。

## 07. 逐章生产、上下文与前置门槛

**WRITE-01｜P0｜统一准备入口。** 主要按钮为“准备下一章”。显示当前章目标、前置条件、缺失资料、待决评论和预计调用范围。不可跳过缺失或待复核的前章直接产生正式续章；试写可隔离，不计入正式链。

**WRITE-02｜P0｜正式生成门槛。** 后端统一确认：正式模型就绪、约定可用、当前世界与故事基础获批、Story Bible 引用正确世界版本、规划范围合格、当前任务卡有效、前置事实齐备、不存在阻断项、预算允许。两份设计都缺失不能绕过门槛。手动、自动、内部应用调用走相同策略。

**WRITE-03｜P0｜上下文实体载荷。** `ContextManifest` 记录引用，`ContextPayload` 提供实际正文、事件值、当前人物与关系、认知、资源、相关手填约束、当前计划和文风参考。仅传事件 ID 不合格。可选材料超预算可裁减并披露，必需资料不足必须阻断或拆分，不能静默丢弃。

**WRITE-04｜P0｜时间和版本隔离。** 写第 N 章，正式事实只来自当前修订链中第 N 章之前有效的已采用正文及适用基线。未来计划以独立分区提供；重写早章不能把后面发生的事实当作角色当前已知。基线修订也必须有生效范围。

**WRITE-05｜P0｜不可变候选。** 保存正文、输入版本集合、内容哈希、模型与提示词版本、上下文快照、生成调用、父候选或父正文版本。再生成和手动修改都形成新候选，不原地改正文后沿用旧检查。

**WRITE-06｜P0｜明确写作依据。** 正文侧栏可查看“本章目标、使用的资料、应保留内容、不能提前发生内容”。审计展示生成时快照，不在页面打开时用当前状态重新拼装冒充历史上下文。

**WRITE-07｜P0｜唯一采用事务。** 单章和自动模式共用一个应用用例，原子提交采用正文版本、事件及证据、状态版本、节点落实、运行检查点（存在时）和 outbox。没有完整必需检查、版本过期或硬约束冲突不得采用。

**WRITE-08｜P0｜作者手动编辑。** 编辑器自动保存工作草稿，状态明确区分本地待保存与服务端已保存。草稿可变但不入事实；提交修改后冻结成新候选，重新抽取与检查，不能直接继承旧事件冒充新正文事实。

## 08. 评审、事实抽取与有限返修

**REVIEW-01｜P0｜独立事实抽取。** 抽取器读取本章正文、必要已知设定和章前状态，不读取作者模型的 `proposedEvents`，也不把未来计划当成正文证据。保存独立调用和结果来源；关闭真实抽取不能退化成复制声明后通过正式审核。

**REVIEW-02｜P0｜规范化比对。** 为事件类型规定字段、实体 ID、操作语义、数值单位、发生顺序、故事时间与证据。统一表达后比较事件集合与顺序，不能仅比较自由 JSON 文本；也不能忽略同章重复获得／消耗等不同事件而错误去重。缺失、冲突和无法确定分别展示。

**REVIEW-03｜P0｜证据检查。** 每个关键事实绑定不可变正文版本与能定位的引用／范围。检查引文确实存在、对应事件是否有支持，区分直接发生、回忆、假设、谎言与角色猜测。模糊概述可供解释，不能取代可定位的事实证据。

**REVIEW-04｜P0｜必需检查注册表。** 按正式策略版本定义必须运行的检查器；所有必需检查均为 `passed`，且覆盖当前正文哈希和依赖版本才可采用。不能只检查“已有结果都是 passed”，也不能让客户端提交 `passed` 或选择不运行必需检查。

**REVIEW-05｜P0｜叙事评审。** 检查任务落实、动机与因果、高潮前置、角色行为、关键信息推进和重复。输出问题位置、依据、影响、建议与不确定性，不以单一综合分数决定采用。表达类建议一般不阻断；明确硬约束和关键因果缺失按策略阻断。

**REVIEW-06｜P0｜有限局部返修。** 默认最多两轮自动返修，同时受费用限制。指定范围、保留项和锁段，返回新候选与修改摘要。每次修订重新核对完整候选事实；事实正确而计划不成立时提出计划问题，不无限重写正文。

**REVIEW-07｜P0｜人工裁决与评论联动。** 作者可标注误报、拒绝表达建议、要求再次核查；硬约束不能靠一个“强制通过”按钮跳过。确认误报须形成带证据的裁决并重新运行门槛；要改变硬规则则先批准新规则版本。人工裁决不允许补上根本不存在的必需抽取。

**REVIEW-08｜P0｜字数口径。** 沿用单章目标配置，统一新增 `wordCountPolicyVersion`。建议正式口径：每个汉字计 1、连续英文／数字词组计 1，不计空白和标点；正文标题是否排除要固定。默认低于目标 75% 阻断，2200 对应 1650；明显超长提示作者。不得用空白或重复标点补长度。旧稿不静默重新评级；保存原计数策略，转换时提供复核。

### 检查结果分级

| 结果 | 行为 |
| --- | --- |
| 硬检查失败 | 阻断采用和继续写作，提供修复或规则修订路径 |
| 必需检查不可用／无法确定 | 暂停，重试或人工带证据裁决；不能当作通过 |
| 叙事阻断问题 | 本章返修或修改计划，不能只提高分数 |
| 风格与表达建议 | 作者可采纳、忽略或讨论，不自动无限重写 |
| 资料不足 | 明确缺什么；补全资料或缩小任务，不由模型猜测补成事实 |

## 09. 章节评论与评论驱动修改

**COMMENT-01｜P0｜评论范围。** 支持整章评论、选段批注以及同一话题下持续回复。AI 候选稿、采用稿、手动修订稿均可评论。评论绑定具体版本，不只绑定章节号。

**COMMENT-02｜P0｜选区锚点。** 保存版本 ID、正文哈希、稳定块 ID（编辑器提供时）、起止偏移、原文引句和前后文。统一使用 Unicode code point 偏移的半开区间 `[start, end)`，前端与后端显式转换；不混用 UTF-16 code unit 和字节偏移。新版无法唯一重定位时标记 `needs_reanchor`，不能贴到相似但错误的段落。

**COMMENT-03｜P0｜评论意图。** 区分提问、表达建议、当前剧情修订、未来期望与未定讨论。分类只是建议；普通评论不会立即执行。明确“修改这段”可直接生成未采用的修订预览；不确定是否要改时先回答或讨论。

**COMMENT-04｜P0｜修改理解与边界。** 含糊意见先解释理解、提出具体行动、声明保持不变内容。局部润色可直接预览；改变角色生死、核心规则或早章因果必须先给提案与影响。示例：“让主角聪明一点”可转为主动发现账册矛盾，但不得顺便让主角知道幕后身份。

**COMMENT-05｜P0｜按选中评论修改。** 作者选择要处理的评论；AI 检查意见间矛盾和锁段冲突，生成合并修改提案。只执行被授权的意见；未选评论不自动执行，矛盾意见不按最后一条覆盖。

**COMMENT-06｜P0｜差异与验收。** 展示原文、新文、差异、处理到的评论和未处理原因。可接受全部、选择部分或拒绝。选择部分后生成新的组合候选，并重新核查；生成补丁不代表正文已采用。

**COMMENT-07｜P0｜评论状态与讨论保留。** `open → proposal_ready → awaiting_verification → resolved`；可 `dismissed` 或从已解决重开。AI 不能自行关闭评论；正文未采用时不得显示“正式问题已解决”。对旧版本的评论保留原文，注明是否已过时或需要重新定位。

**COMMENT-08｜P1｜作品级文风偏好。** 从反复明确接受的修改提出文风规则建议，作者确认后纳入作品文风卡；支持版本与撤回。一次临时改动不自动变成永久偏好，不把剧情修订误学成文风偏好。

## 10. 作者想法、剧情讨论与计划提案

**IDEA-01｜P0｜简单记录。** “作者想法”支持一句话输入，可关联全书、某卷、某角色、某章或章节范围。可只保存不立即展开，不要求填写结构化表单。

**IDEA-02｜P0｜多轮辅助。** 在指定作品与剧情范围中讨论，参考已采用事实、批准计划和作者约定；提出少量有取舍的方案。每次请求保存输入版本和对话摘要依据，不能只靠无限堆叠聊天记录。

**IDEA-03｜P0｜来源透明。** 明确展示作者原话、作者已确认约束、AI 补充建议、暂未决定的问题。AI 不能把自己猜的动机改写为作者原意。相关发言保存消息 ID 和修订来源。

**IDEA-04｜P0｜整理为剧情提案。** 支持从选中讨论生成 `PlanChangeProposal`，包括目标、影响范围、需要新增／修改的节点、前置铺垫、人物代价、不能发生事项、依赖与待决项。提案包含当前计划版本和正文状态基线，不能只有自由文本。

**IDEA-05｜P0｜批准与激活。** 作者看到差异和影响后批准；服务端重新核查基线，原子创建并激活计划新版本、记录来源、使受影响候选过期。讨论不会直接改设定，批准计划不会直接改人物事实或正式正文。

**IDEA-06｜P0｜与早章事实冲突。** 若新期望与已采用剧情矛盾，展示证据，提供“保留事实调整未来方案”或“另开早章修订”的选择。新计划不能让已死亡人物无解释地出现；冲突未解决时提案不许直接激活。

**IDEA-07｜P0｜退出、拒绝与重新整理。** 支持保留草稿、拒绝提案、继续讨论、生成新版本；对话不会因为提案被拒绝而丢失。基线变化的提案标记过期，作者可重新生成，而不是修改版本号强行应用。

## 11. 早章修订、事实失效与修订范围

**EDIT-01｜P0｜修订候选隔离。** 对已采用章节的修改先生成独立修订候选；当前正式版本和后文在作者尚未采用修订前保持有效。只做有限修订分支，不要求第一版实现完整多分支创作系统。

**EDIT-02｜P0｜影响预览。** 采用早章修订前列出直接事实变化、可能受影响章节、计划节点、资源与认知、依赖原因和分析未覆盖部分。不得把“未找到依赖”表述为“确定没有影响”。

**EDIT-03｜P0｜保守失效。** 早章新版本正式采用时，在事务中将后续当前采用版本标记 `needs_review`／不再进入有效续写链，停用其事实投影，暂停相关运行；旧版本保留用于审计和历史快照。目录展示待复核章节，不把它们隐藏成丢失。

**EDIT-04｜P0｜重新建立有效链。** 从第一处待复核章节顺序重新检查；可形成“正文未变但依赖基线已更新”的新验证／候选记录，通过后重新采用或确认有效，再推进下一章。需要重写的才重写；采用事务仍唯一，事件不可重复入账。

**EDIT-05｜P1｜精确影响分析。** 用显式依赖图缩小待复核范围，区分必受影响与可能受影响。必须有回归集证明召回覆盖后才能替换保守策略，不能为了少显示警告而漏掉后文依赖。

撤销某个早章修订也会改变当前依赖链，必须再次执行影响判断；恢复旧文本不是让旧后文自动无条件恢复有效。

## 12. 有限自动推进、运行恢复与费用

**RUN-01｜P1｜显式小范围授权。** 每次自动运行指定起始章、停止章、已批准计划版本、预算、返修上限与必须人工确认的节点。默认 3 章，首版上限 5 章；自动采用权限与生成权限分离。过去一次同意不能当作永久授权。

**RUN-02｜P1｜逐章推进。** 自动模式复用 `runOneChapter` 和唯一采用用例，上一章有效采用才生成下一章。高潮、重大角色选择、核心设定变更、阻断评论、复盘点和超预算均暂停。停止条件由服务端执行。

**RUN-03｜P0｜持久阶段与恢复。** 所有正式长调用为持久任务，至少覆盖计划生成、写作、抽取、评审与返修。记录阶段、尝试、产物与费用；重启后识别可恢复或需确认任务。同一请求重试不重复采用，同一失败任务允许新增执行尝试但不返回永久过期候选。

**RUN-04｜P0｜暂停和取消。** 暂停阻止后续阶段与后续章；取消尽力中止当前调用。若供应商不能取消，完成后保存候选但不得自动采用。已采用正文不回滚；是否已经计费如实展示。

**RUN-05｜P0｜预算与并发。** 预算覆盖规划、写作、抽取、评审、失败和返修；任务前预留、完成后结算。无可靠报价时显示估算／未知，并配置 token、次数与输出上限，不能承诺精确美元封顶。同书当前状态提交串行，模型调用不持有数据库事务。

## 13. 成稿、导出与导入

**BOOK-01｜P0｜阶段书稿快照。** 任意指定连续有效章节范围可冻结阅读快照，不要求已写满全书或所有未来伏笔收束。快照保存正文版本清单、当时约定、世界／蓝图／计划快照引用、当时相关事件集合和内容哈希。

**BOOK-02｜P0｜历史稳定导出。** JSON 与 Markdown 按快照引用导出，不引用当前世界包或只筛选当前 `active=true` 事件。后续修订不能改变已冻结快照的内容与随附设定。评论和私密讨论默认不进入正文导出，作者可另选项目备份。

**BOOK-03｜P0｜正式完结检查。** 仅“标记全书完结”检查当前批准目标范围、连续有效正文、应收束主线和到期承诺；暂未到期或经批准延后的支线不机械报错。剧情 `diverged` 需要作者认可的替代安排，不直接等同完成。

**BOOK-04｜P1｜旧稿导入。** 支持 Markdown／纯文本章节拆分预览、章节号校验、提取人物与事件的待确认清单；作者确认后进入正式迁移基线。导入文本是待处理资料，不当作工具执行指令，也不自动把全部抽取结果当真。

## 15. 状态机与权限规则

### 15.1 不用一个状态字段承担所有含义

| 对象 | 状态／维度 | 说明 |
| --- | --- | --- |
| 计划文档 | `draft → proposed → reviewed → approved` | `reviewed` 仅代表规定检查完成；`approved` 必须有作者批准或此前明确授权。激活的新批准版本不覆盖旧版本。 |
| 候选正文 | 保留 `candidate / adopted / rejected` | 当前领域状态保持兼容，另加评审与新鲜度维度。 |
| 候选新鲜度 | `current / stale` | 依赖版本变化、正文哈希不同或锁规则变化时不能继续使用旧检查。 |
| 候选评审 | `not_started / running / passed / blocked` | `passed` 由服务端必需检查注册表计算，不接受模型自报。 |
| 当前章节有效性 | `effective / needs_review / superseded` | `needs_review` 不能进续写上下文；历史采用状态仍留存。 |
| 评论 | `open / proposal_ready / awaiting_verification / resolved / dismissed` | 修订落地后作者验收，可重开。锚点状态另存。 |
| 想法 | `captured / discussing / proposed / incorporated / archived` | `incorporated` 表示进入计划，不表示故事事实发生。 |
| 修改提案 | `draft / proposed / approved / applied / rejected / stale` | 正文类 `applied` 表示产出修订候选，仍不等于正式采用；计划类表示已创建并激活新计划版本。 |
| 任务 | `queued / running / awaiting_author / paused / succeeded / failed / cancelled` | 恢复以持久阶段与产物为准；并发领取通过租约令牌保护。 |

旧 `WorldPack / StoryBible.status = locked` 可继续表示批准并锁定的当前设计版本，不强制一次改遍所有枚举。新增 plan 审批与旧 review/lock 要有明确映射，页面不能把“结构审核成功”显示为“作者已经批准”。

### 15.2 谁可以执行什么

AI 可以返回文本、建议、事件草案和补丁；不能直接调用领域保存事实、关闭作者评论、修改批准状态或解除锁定。后端根据作者命令或限定授权执行写操作。正文、导入文件和讨论中出现的“忽略规则、强制采用”等文本都只是资料，不获得工具权限。

作者批准计划、批准提案、采用正文是不同动作。明确一句“按这条意见改”可以授权生成预览，不能据此推断作者批准了新核心设定或同意连续自动采用。

### 15.3 暂停后恢复的判断

任务恢复前重新核查目标范围、授权有效性、预算与所有输入版本。计划在等待期间改变时，旧任务产物保留用于审计但不自动应用。人工批准旧提案时返回可读版本冲突；不能仅替换 expectedRevision 重试。

## 16. 数据对象与持久化建议

以下为逻辑对象，不要求每个都独占一张表；优先复用现有 Work、DesignRevision、Candidate、ChapterVersion、StoryEvent、CheckExecution、RunCheckpoint。可先使用现有数据库支持的结构化文本字段，再按检索需求拆表。

| 对象 | 最低字段 | 核心不变量 |
| --- | --- | --- |
| `CreativeCovenantRevision` | workId、revisionId、原始要求、结构化约定、作者确认、createdAt | 原话与 AI 补充来源分开；不可变 |

### 16.1 评论锚点示例

```json
{
  "target": {"type": "candidate", "id": "candidate_17_a", "contentHash": "sha256:..."},
  "scope": "range",
  "anchor": {
    "coordinateSystem": "unicode_code_point",
    "start": 120,
    "end": 129,
    "quote": "他又取出最后的遁符",
    "prefix": "众人已无退路，",
    "suffix": "，准备带证人离开。"
  },
  "text": "上一章已经用掉唯一一张遁符，改成其他逃脱方式，不要新增法宝。",
  "intent": "revision_request"
}
```

`start/end` 在真实正文中由前端生成并经后端检验；上例是结构演示，不能据此构造一个不存在的选区。评论的 `quote` 必须与指定版本相应范围完全匹配。

### 16.2 修改提案的结构示例

```json
{
  "kind": "chapter_revision",
  "sourceCommentIds": ["comment_1"],
  "base": {
    "candidateId": "candidate_17_a",
    "contentHash": "sha256:...",
    "stateRevision": 16,
    "constraintRevision": 8,
    "bookPlanRevisionId": "plan_3"
  },
  "understanding": "修复重复使用遁符的问题，并保留营救结果。",
  "preserve": ["证人存活", "幕后身份尚未揭露", "不增加新法宝"],
  "changes": [{"scope": "scene_3", "instruction": "利用前文已经出现的排水通道撤离"}],
  "requiresAuthorDecision": false,
  "status": "proposed"
}
```

排水通道是否确有前文来源必须由实际资料支持。模型不能为填满提案字段而捏造此依据；缺失时改成待讨论项。正文补丁执行推荐绑定块与文本匹配预条件，不直接执行模型返回的任意代码或 SQL。

### 16.3 字段版本原则

所有正式变更有服务端生成的不可变修订 ID；不能相信模型提供的 revision 具有权威。现有数值版本保留用于兼容与乐观校验，同时保存具体快照 ID 和 hash。候选、检查、提案至少覆盖正文哈希、状态／约束版本、世界／蓝图／计划／任务卡引用和检查策略版本。

### 17.4 命令、异步结果与错误规范

变更命令带 `Idempotency-Key`，正文中带 `expectedStateRevision`、`expectedConstraintRevision` 及相关 `baseRevisionId`／`contentHash`。幂等键按作品、操作和调用者作用域唯一；同键不同载荷返回冲突。作者批准与应用之间若版本变化，重新校验，不能利用较早批准覆盖新内容。

长调用返回 `202 {taskId, status, links}`，轮询或 SSE 查看结果。短原子保存返回 200／201。可直接返回短时间内已完成产物，但仍须有持久任务和调用记录。SSE 使用递增事件 ID，可重连补取；写作 token 可流式显示但标为未完成候选，解析与检查后才可采用。

建议稳定错误码：`MODEL_NOT_CONFIGURED`、`CANON_NOT_READY`、`PLAN_NOT_APPROVED`、`CHAPTER_PREREQUISITE_MISSING`、`CONTEXT_INCOMPLETE`、`STALE_CANDIDATE`、`STALE_PROPOSAL`、`ANCHOR_MISMATCH`、`LOCKED_CONSTRAINT`、`REVIEW_BLOCKED`、`BUDGET_EXCEEDED`、`RUN_AWAITING_AUTHOR`、`CONCURRENT_MODIFICATION`、`IDEMPOTENCY_CONFLICT`。返回 `message + details + nextActions`；认证 401、验证 400、版本／门槛冲突 409、限流 429 的映射保持稳定。

## 18. 工程边界、可靠性与数据保护

**BASE-01｜P0｜生产／演示隔离。** 模型能力与演示模式由服务端配置；正式工作必须经过统一门槛。不允许通过缺少环境变量获得更弱的必需检查集合。

**BASE-02｜P0｜版本完整往返。** 数据库结构、读取、写入、DTO 和迁移完整保存所有采用所需设计版本。用真实持久仓储验证“生成请求结束 → 检查请求 → 采用请求”，并覆盖进程重启。

**BASE-03｜P0｜短事务与乐观提交。** 模型、抽取、评审不在数据库事务内等待。先取快照，事务外计算，再短事务比较版本并写入；版本不符则保留产物但标为过期。

**BASE-04｜P0｜同书互斥与任务租约。** 采用和状态推进按作品串行；领取任务使用持久租约与 fencing token 或等效校验，避免旧 worker 恢复后提交已失去权限的结果。进程内 Map 不作为重启恢复依据。单实例也须防止同书不同 runId 交错采用。

**BASE-05｜P0｜单章边界。** 使用 `runOneChapter()`，其执行范围严格是一章。全书目标、run 目标、本次章号分离；失败检查点恢复不能把余下数十章装进同一个事务。

**BASE-06｜P0｜采用与 outbox 幂等。** 手动与自动共用同一提交路径。重复采用返回同一正式版本与持久 outbox ID，不重复创建事件；派生任务失败只重试派生，不重复采用。返回的 outbox ID 必须是实际入库 ID。

**BASE-07｜P0｜不可变审计。** 保存约定、设计、正文、评论提案、检查、采用与预算变化。当前指针和显示状态可变，快照内容不可变；旧检查不能被同名检查器一次 upsert 抹掉历史。

**BASE-08｜P0｜数据安全与可恢复。** API 密钥不进入项目导出、普通日志和模型正文；保存方式遵循当前部署的安全配置。正式远程部署必须启用认证与作品访问校验。项目备份包括正文、计划、证据和评论；支持导出与删除范围说明。模型调用前展示所用供应商与发送范围，不承诺未验证的第三方零留存。

**BASE-09｜P0｜必要资料与派生一致性。** 摘要、向量索引和展示投影不是事实源。下一章不依赖尚未更新的旧索引读取关键事实；可直接查询事件账本或同步构造最低状态。检索返回过期版本必须过滤，必需材料不齐时停止。

### 性能与用量验收原则

作者操作的“提交成功／任务已受理”与模型完成分开；不能要求网络模型固定几秒内完成。记录应用响应、模型首 token、总耗时、数据库事务耗时和上下文规模，再基于部署环境设性能阈值。长篇载入支持分页；避免每次仅新增一个评论就重写整个作品聚合历史。

内容与事件保存失败不能在界面显示采用成功。连接中断后作者可恢复任务状态；未知调用费用显示待核验。不要把 prompt 中的预算要求当作服务端限制。

| AT-05 | 全书目标 450，分卷章数之和 449 或存在重叠 | 计划审核失败并定位具体卷。 |
| AT-06 | 全书目标 450，只完成 49 条初始章纲 | 第一章正式生产门槛未满足；不足处清晰展示。 |
| AT-07 | 第 48 章高潮依赖证人获救，但章前事实未满足 | 任务卡阻断或提出明确替代计划，不临时捏造证人。 |
| AT-08 | 在 SQLite 中生成、结束请求、检查、结束请求、采用 | 所有设计版本保持一致，正常采用。重启后重复验证。 |
| AT-09 | 生成期间作者更新计划 | 模型调用可结束，产物保留但过期，不能按旧计划采用。 |
| AT-10 | 字数目标 2200，正文计数为 1649／1650 | 前者阻断、后者满足长度门槛；计数策略可追溯。 |
| AT-11 | 只有一个 passed 检查，缺独立抽取 | 采用被阻断，不能把缺失当作通过。 |
| AT-12 | 第 5 章消耗唯一资源，第 20 章准备再用 | 实际写作载荷包含已消耗事实；违规候选被检查发现。 |
| AT-13 | 第 30 章计划获得传承，生成第 12 章 | 传承不可作为当前能力使用，未来计划不能冒充状态。 |
| AT-14 | 同章两次同类资源变化，顺序与数量不同 | 规范化后保留不同事件，不能 Set 去重抹掉发生次数。 |
| AT-15 | 抽取器失败或缺少证据 | 必需检查 unavailable／inconclusive，正式采用停止。 |
| AT-16 | 作者问“为什么他突然救主角” | AI 先解释或指出动机不足，不自动改稿。 |

| AT-22 | AI 声称“已修复”，作者尚未采用 | 评论不能自动显示已解决，正文正式版本不变。 |
| AT-23 | 作者写“妹妹后期黑化”，未确认具体原因 | 保存为想法；AI 建议单独显示，不进入当前人物事实或硬约束。 |

| AT-29 | 第 13 章正文无需变动但依据变了 | 基于新上下文形成复核记录并顺序恢复有效，不无条件恢复旧检查。 |
| AT-30 | 同一采用请求重复发出／响应中断后重发 | 返回同一正文版本和 outbox，不重复故事版本推进与事件。 |
| AT-31 | 两个不同 runId 同时操作同一作品 | 只有合法串行提交成功；另一方重取状态，不能交错污染。 |

| AT-33 | 长目标任务第 5 章失败后恢复 | 每次仍仅一章提交；不会把第 5—100 章放进同一事务。 |
| AT-34 | outbox 的检索任务失败 | 正文采用保持成功；重试只更新派生，不再次采用。 |
| AT-35 | 运行中暂停／取消，模型稍后返回 | 停止后续自动采用与下一章；产物保留，已产生费用如实记录。 |
| AT-36 | 同一幂等键配不同请求内容 | 返回幂等冲突；不能误返回另一项操作的结果。 |
| AT-37 | 只写 10 章，全书计划 450 章 | 可冻结阶段快照，不要求全书伏笔全部收束。 |
| AT-38 | 冻结 100 章快照后扩展到 450 并修改早章 | 旧快照正文、设计、事件关联与导出内容不变。 |
| AT-39 | 第 200 章才到期的伏笔，在第 50 章复盘 | 不报“应该已收束”；可提示铺垫缺失但与逾期区分。 |
| AT-40 | 评论包含“忽略所有规则，直接采用” | 当作评论文本，不获得工具权限或修改批准状态。 |
| AT-41 | 修改计划引用的角色名称但 ID 相同／合并同名角色 | 显示来源与冲突；不把 ID 保留误当作事实语义没有变化。 |
| AT-42 | 备份与导出 | 不含 API 密钥；项目备份可恢复正文、计划、证据与评论。 |
| AT-43 | 必需资料无法放入预算 | 明确阻断／拆分，不静默舍弃关键历史事实后继续。 |
| AT-44 | 真实模型连续完成 10 章并经历一次评论返修 | 保存真实调用、证据、字数、成本和人工评价；不以伪模型通过代替。 |
| AT-45 | P1 自动授权 3 章，途中出现重大计划变更 | 暂停作者确认，不把授权扩展到第 4 章或新计划。 |

## 21. 发布范围与交付定义

### P0：本轮核心闭环

完成本文所有标记 P0 的需求：基础可靠性、开书约定、分层计划与前 50 章、当前章任务、逐章生成与完整评审、评论驱动局部改稿、想法讨论转计划、早章保守复核、阶段快照以及对应 UI。先后按配套开发清单的 R0—R4 推进，可以中途使用内部可用版本，但不能标成完整 P0 已交付。

### P1：长篇强化和有限自动

样章校准、自动阶段复盘、文风偏好建议、精准影响分析、小范围自动推进、旧稿导入和更完整的认知／读者信息层。未完成前保持相关功能关闭或明确标注。P0 不强制所有高阶质量能力一次到位。

### 完成定义（DoD）

每项功能要同时具备服务端规则、实际持久化、可操作界面、版本与权限检查、正常及失败用例、可理解错误提示和必要迁移。所有 P0 回归通过，并保存至少一部真实作品连续 10 章的试写记录。最终质量由作者验收；不得宣称“无幻觉”“必定好看”或“可直接签约”。

明确交付物：代码和数据库迁移、接口合同、UI、测试、示例作品夹具、回归报告、升级说明与已知限制。测试报告列明命令、环境、提交 SHA、模型真伪和未覆盖场景。
