# 页面交互、自动化边界与验收方案

版本：v0.4
日期：2026-10-09  
对应：PRODUCT-AND-ARCHITECTURE.md  
状态：产品设计，不代表这些功能已实现。

## 1. 这一轮的产品决策

1. 默认尽量自动完成创作。用户无需逐章确认大纲、正文、事实提取或返修。
2. 开书时允许一次性指定系统可以自行调整的范围，以及必须保留的设定。
3. 系统在范围内自动执行并保留证据；无法解决的冲突只阻止受影响内容继续采用或发布。
4. 试写用于校准风格与方向，文风认可与剧情采用必须分开。
5. 用户明确锁定的正文与设定具有更高约束力；模型不能自行解除锁定。
6. 长篇质量用正文样本、已知问题案例和运行反馈评估，不能仅用模型自评分。
7. 先完成个人使用的完整流程，现阶段不加入多用户商业平台、社区或模型训练。

## 2. 用户第一次使用的完整过程

### 2.1 配置模型

填写服务地址、协议、模型与 Key；服务端测试连接和必要能力。初期可以为所有角色使用同一个模型配置，之后按需要把规划、正文、审查与事实提取分开。

系统展示可用能力、测试结果与具体失败原因。若供应商没有明确价格配置，费用显示“未知”，不能将其当作免费；调用量单独记录。

### 2.2 新建作品

入口分为“展开我的创意”和“帮我找故事方向”。

共同字段：
- 题材与子风格；第一版开放玄幻。
- 想吸引的读者与希望带来的阅读体验。
- 主角或故事的核心吸引点。
- 必须保留的想法、锁定关系、避免元素。
- 预计长度、单章字数与更新节奏；未确定时使用可调整的建议值。

创意模式：系统提取用户的明确要求，区分原文要求与自行补充的建议。
方案模式：提供少量差异明显的方案，展示故事承诺、核心人物、冲突来源和长篇发展空间，用户选择后进入同一流程。

### 2.3 建立基础计划

系统自动生成：
- 世界规则、人物与关系。
- 全书目标、结局方向与分卷安排。
- 开篇阶段的章节和场景计划。
- 仍未确定但不阻碍开篇的内容。

未来剧情保留适当弹性。凡是系统补充而非用户锁定的内容，在允许范围内可以调整；重大调整显示原因、版本和影响。

### 2.4 试写与校准

使用同一开篇计划形成可比较的样章，避免用完全不同的情节掩盖文风差异。样章页提供：
- 阅读全文与并排比较。
- “喜欢这段表达”“避免这种表达”。
- “设为文风参考”。
- “采用为正式章节”。
- “调整要求后重试”。

用户可选择自行比较，也可让系统先按创作约定初选并继续。系统初选必须标明来源，不能显示为“作者已认可”。

只认可风格：保存参考片段和表达特征，不导入样章事件。
采用剧情：执行完整的章节检查与采用流程，按章节顺序提交故事状态，并从下一章继续写。
都不采用：保存为试写历史，不影响正式故事。

### 2.5 开启自动创作与发布

作品级配置保存：
- 单章字数区间。
- 日更计划与时区。
- 合格存稿目标。
- 返修次数、任务调用上限。
- 允许系统自动改动的范围。
- 模型与文风版本。
- 平台连接与发布规则。

可以先写作，再绑定平台。平台未配置或尚未验证时，创作继续，发布显示“未配置”，不能显示已启动自动更新。

## 3. 核心页面布局

### 3.1 作品总览

顶部：
- 作品名称、创作运行状态、发布状态分别显示。
- 开始/暂停/继续操作。
- 当前采用字数、合格存稿数、下一次更新安排。

中部：
- 当前卷：目标、关键节点进展与剩余任务。
- 最近活动：新采用章节、关键人物变化、返修结果。
- 需要处理的问题：原因、影响范围、可采取的动作。

下部：
- 阅读反馈与经营观察。
- 模型调用量、可获得的费用统计。
- 最近备份状态。

从总览可以直接打开受影响章节。前端进度以已完成步骤和当前阶段展示，不编造总耗时或完成百分比。

### 3.2 章节工作台

左侧：分卷章节目录，区分候选、采用、待重新检查、合格存稿和已发布状态。

中部：正文阅读/编辑与版本切换。用户选中段落后可以：
- 只调整措辞。
- 保留事件，修改表达与节奏。
- 重写当前场景。
- 按特定问题修复。
- 锁定/解除本人锁定的段落。

右侧：与当前选择相关的面板：
- 修改请求：范围、目标、必须保留项。
- 审稿问题：正文证据、设定依据、修复建议。
- 人物与故事状态：本场景开始时的相关事实。
- 修改差异：候选改动与采用稿对照。

底部：任务状态、保存状态、采用操作。自动任务的操作也通过同一业务流程完成，不能绕过版本校验。

### 3.3 文风与样章

放在作品的“世界与人物”工作区内作为子页，不增加新的全局导航。

展示：
- 读者定位与核心吸引点。
- 人称、视角、信息披露边界。
- 表达偏好：对白、描写、叙述距离、节奏等。
- 认可样段、反例及用户备注。
- 文风版本和后续任务生效范围。

风格参考中的实体、台词与事件只是示例。需要复用为真实设定时，必须通过相应采用流程。

### 3.4 质量与问题

问题按“确定冲突、语义疑点、信息不足”分类，也可按人物、章节、卷和严重程度筛选。

每条问题显示：
- 具体位置与文本。
- 为什么提出。
- 相关设定或前文证据。
- 建议的最小修复范围。
- 当前处理状态和已尝试的修订。
- 是否阻止采用或发布。

增加文学质量视图：重复表达、视角跳转、对白辨识、场景有效变化、情绪铺垫等。所有语义报告保留不确定性，不把偏好当成客观事实。

### 3.5 模型配置与评测

全局管理服务连接；每部作品选择规划、写作、审稿、提取角色所用的配置。

每次升级形成候选版本，展示：
- 旧配置与新配置的差异。
- 固定场景评测结果。
- 失败案例、正文差异和调用消耗。
- 哪些作品与后续任务将切换。
- 上一个可用配置。

评估任务不会直接改变作品的采用稿、故事状态或发布队列。

## 4. 四个关键状态流程

### 4.1 样章：两条独立状态

生成状态：
draft → generating → completed / failed

文风参考状态：
unreviewed → system_selected / author_selected / rejected

剧情状态：
noncanonical → adoption_checks → adopted / rejected

风格选中不触发剧情采用。样章跨多章时，采用按顺序进行，并重新核对前置状态。

### 4.2 编辑：范围先于生成

requested → generating_patch → validating → candidate_ready → adopted
                                    ↘ conflict / stale / failed

编辑请求固定基础正文版本与允许范围。生成器提交替换段落列表，不允许直接覆盖整份采用稿。

保存前程序验证：
- 基础版本仍是请求对应的版本。
- 所有替换都落在允许范围内。
- 锁段内容未变化。
- 未授权段落未变化。
- 段落结构仍然有效。

“保留事实但改写表达”包含语义判断，需要额外审查，不能只靠文本校验值证明。

若版本已变化，重新比较与重新生成候选补丁；不静默覆盖。采用失败时保持原正文不变。

### 4.3 模型配置

candidate → evaluating → eligible / rejected
eligible → active_for_project → superseded / rolled_back

模型配置全局可复用，启用记录按作品保存。默认升级通过评测后由用户选择作品启用；用户可以另行设置明确的自动切换策略。

正在执行的写作链固定使用启动时的配置版本。切换在后续任务边界生效，避免同一条修订链中途更换策略。正文回退与配置回退分开操作。

### 4.4 阅读反馈

raw → organized → observation → proposal → accepted / deferred / rejected

反馈记录需要包含来源、时间、覆盖章节、原话或指标定义。作者主观判断和平台指标分别标注。

提案说明：
- 观察到什么现象。
- 有哪些支持与反对证据。
- 可能原因与不确定性。
- 建议修改哪些内容。
- 修改后的观察目标。

反馈本身没有正文编辑、设定修改和发布权限。提案执行时仍检查作品预设的自动化范围：局部措辞等允许事项可自动处理，涉及作者锁定内容时等待作者决定。

## 5. 自动化边界

以下是建议默认值，可按作品调整。

| 操作 | 默认行为 |
| --- | --- |
| 生成下一章、提取候选事实、执行审稿 | 自动 |
| 在未锁定范围内修复明确问题 | 自动，受返修次数和调用上限约束 |
| 采用检查通过且输入版本仍有效的正文 | 自动 |
| 补足未锁定的近期剧情计划 | 自动，保留变更原因 |
| 改变作者锁定的身份、关系、结局要求或正文 | 不自动，生成冲突与可选方案 |
| 修改未发布的后续章节 | 在已配置改稿范围内自动，必须重新审查 |
| 修改已发布章节 | 单独的修订任务，不混同日常自动更新 |
| 首次绑定平台、选择账号和作品 | 需要配置；此后按已授权规则运行 |
| 到时间发布已通过检查的章节 | 在平台接入有效时自动 |
| 提交结果未知 | 先核验，不直接重发 |
| 模型升级与正文重写 | 分开处理，升级不触发整书重写 |
| 阅读反馈改变主线或已锁定文风 | 先形成可审查提案，不直接执行 |

阻断问题只影响其依赖范围。同一作品后续章节如果依赖未解决事实，会等待；其他作品和没有依赖的合格存稿可以继续运行。

## 6. 最小数据与服务契约补充

新增对象的职责：
- StyleProfileVersion：读者定位、视角、表达约定、参考片段、反例与来源。
- SampleRun：试写输入、候选版本和比较结果。
- StyleReference：引用具体文本版本，区分系统初选与作者认可。
- EditRequest：基础版本、允许范围、修改目标和保留项。
- EditLock：锁定段落、内容校验值、创建人和适用范围。
- ModelConfigVersion：模型、参数、提示词版本、结构化输出能力与工具能力。
- EvaluationCase：输入事实、场景、已知期望和已知错误；不全部塞进实际生成提示词。
- EvaluationRun：配置组合、逐案例结果、证据、用量。
- ConfigActivation：作品采用哪个配置，从哪一批后续任务开始。
- FeedbackEntry：原始试读意见及来源。
- MetricSnapshot：指标定义、取数窗口、单位、来源和缺失状态。
- Observation、ChangeProposal：证据、建议、权限范围、后续处理结果。

API 示例，均为建议：
- POST /books/:id/samples
- POST /books/:id/style-profiles
- POST /chapters/:id/edit-requests
- POST /chapters/:id/locks
- POST /model-configs/:id/evaluations
- POST /books/:id/model-activations
- POST /books/:id/feedback
- GET /books/:id/observations

所有写入请求校验目标作品、基础版本与权限。长任务接口返回任务 ID，结果通过查询或 SSE 获取。

## 7. 验收案例

### 7.1 不变量与故障场景

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| A01 | 选中样章文风，但样章里哥哥死亡，正式稿中哥哥存活 | 正式故事不新增死亡事实 |
| A02 | 将前两章样章正式采用后启动续写 | 从下一章继续，不重复生成已采用开篇 |
| A03 | 要求只改第二段，模型修改第三段 | 候选补丁被拒绝，采用稿保持不变 |
| A04 | 自动返修改动已锁定台词 | 锁段校验失败，不自行解锁 |
| A05 | 模型工作期间作者已提交新版本 | 旧结果标记过期，不能覆盖新正文 |
| A06 | 当前正文存在只能通过修改锁段解决的硬冲突 | 暂停受影响内容，展示冲突和处理选项 |
| A07 | 模型升级评测生成新人物死亡情节 | 评测输出不污染任何作品事实 |
| A08 | 正在执行写作任务时启用新模型版本 | 当前任务使用原绑定版本，后续任务按启用规则切换 |
| A09 | 回退模型配置 | 不删除、不重写已采用稿或已发布快照 |
| A10 | 导入一条“杀死主角”的读者意见 | 作为反馈保留，不执行写作或发布指令 |
| A11 | 平台未提供追读数据 | 显示未知，不显示为零，不推断读者全部流失 |
| A12 | 将关系“师姐”锁定，正文写为亲姐姐 | 输出带来源的冲突，不更新为血缘关系 |
| A13 | 候选稿给出物品转移，采用稿未发生转移 | 物品仍属采用稿中的持有人 |
| A14 | 修改早章的获知秘密时间 | 依赖旧时间的后文和审查结果进入重新验证 |
| A15 | 平台提交超时但实际发布成功 | 核验后记录成功，不重复提交 |
| A16 | 工作进程在采用事务附近中断 | 正文版本与状态更新同时存在或同时未提交，可恢复 |

### 7.2 语义质量评估

准备有人工标注的正反案例：
- 谨慎角色为救亲人冒险，有充分动机；不应机械判定崩人设。
- 冷酷角色突然无私，缺乏事件与选择支撑；应指出缺口。
- 平静章节推进关系和伏笔；不应只因没有战斗判为注水。
- 几个配角目标、表达与选择都能互换；应提出具体辨识度问题。
- 配角完成重要任务，但主角仍作出核心代价选择；不应机械判为喧宾夺主。
- 时间模糊且允许传送；不能凭空编造旅行时长来判错。
- 读者知情而人物不知情；应检出越界使用信息。
- 有效伏笔尚未兑现；与无目的重复场景应区分。

记录发现了哪些问题、漏掉了哪些问题、哪些报告不成立、修订是否真正改善以及是否引入新问题。质量阈值需依据基线试验确定，不预先宣称达到某个准确率。

### 7.3 连续创作试运行

同一部作品连续创作 10—20 章：
- 观察读者能否理解主线、记住核心角色、愿意继续阅读。
- 检查角色变化与关键选择是否有依据。
- 统计章节采用、返修与阻断情况，定位最常失败的阶段。
- 验证暂停、服务重启、早章修改和继续生成。
- 核对具体版本是否进入存稿与发布记录。

另用跨卷历史资料测试远距离关系、物品、伏笔和时间依赖。短程试运行是流程验证，不等于长篇质量已得到全面证明。

## 8. 交付顺序

1. 基础服务：作品、API、模型调用、版本、任务持久化与恢复。
2. 最小创作闭环：开书、设定、章节计划、候选生成、规则检查、正式采用、故事状态同步。
3. 创作控制：试写校准、精确编辑、锁段、版本差异。
4. 深度质量：人物弧光、群像、节奏、变更影响、跨卷证据。
5. 连续存稿与质量验证：10—20 章试运行、固定案例评测、模型配置升级流程。
6. 首个平台闭环：投稿、章节更新、核验与异常恢复；平台可行性调查在第一步就开始。
7. 轻量反馈和运营：试读记录、可获得指标与有证据的改进建议。

以上阶段可以在低耦合部分并行，但不能让自动发布绕过采用、版本与质量条件。

## 10. 开源对照后的最小交互增补

章节工作台的“本章依据”抽屉必须显示四组内容：必需约束、目标剧情与前置条件、允许读取的已采用证据、仅供参考的历史材料。每条显示来源版本；未纳入材料显示原因。抽屉顶部显示 ready / needs_split / blocked，不能用“上下文已加载”替代完整性状态。

剧情节点旁显示“计划／正文落实／故事事实”三列。邻章只读上下文中的相似内容不能计为本章落实。大纲计划与正文偏离时，系统保留正文，提示继续、调整计划或创建修订提案。

质量中心按检查项显示执行状态。模型超时、结构化输出无效、正文抽取失败和来源版本过期均是可见状态；没有执行成功的必需检查不能显示“通过”。

采用完成后，章节页把“正文采用、状态事件提交、摘要更新、索引更新、发布资格”分开显示。索引或摘要失败时保留已采用正文，任务中心提供重试；下一章如果必须依赖未更新投影，则等待或回读权威正文状态。

本轮新增验收案例应优先验证：必需关系装不下时阻断、计划物品未在正文交付时不改变持有人、声明与正文变化不一致时不入账、检查器不可用时不发布、索引失败时不重复采用。

## 9. 本轮收敛结果

四项补充进入已有页面与业务模块，无需额外扩大主导航。

第一版成功标准：用户能从开书到连续产稿，随时查看和控制关键内容；任务可恢复，正文与事实对应，问题可追溯；在已验证平台上完成正确的投稿和发布。

最终仍需要用户提供或选择的外部信息包括：实际 API 协议和模型、目标平台、部署位置。平台确定前完成适配器契约和可控测试，不能把模拟提交描述为真实投稿成功。
