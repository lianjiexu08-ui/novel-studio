# Novel Studio 开发任务清单 v2.0

> 配套文档：`novel-studio-PRD-v2.0.md`。日期：2026-10-10。
> 目的：把需求转成能分批实现、能回归验收的任务。所有复选框初始未勾选，表示本轮未验收，不意味着仓库完全没有相应代码。
> 阅读基线：`47f0757a2d361a285cbbbb71f3b8fe7b2f70b349`。本次仅整理需求与静态代码衔接，没有修改仓库或运行测试。

## A. 建议执行方式

先完成 R0，避免在版本和事务不可靠的基础上叠加评论／讨论。之后按 R1 规划、R2 逐章工作台、R3 评论与讨论、R4 修订成稿验收推进。R5 是 P1，P0 没验收前不开放有限自动模式。

每个任务先补测试或夹具，再实现领域／应用逻辑与持久化，再接 API 与 UI，最后跑真实数据库与失败路径。不要只补页面，也不要只增加提示词就宣布功能完成。一个任务完成的必要条件见 PRD 第 21 节 DoD。

## B. 依赖关系与阶段出口

| 阶段 | 依赖 | 交付目的 | 阶段出口 |
| --- | --- | --- | --- |
| R0 基础闭环 | 无 | 版本、事务、检查、采用与任务可靠 | SQLite 分步生成／检查／采用成功，重启不丢依据，演示稿不能混入 |
| R1 规划系统 | R0 | 全书／分卷／前 50 章／当前章任务 | 能批准一个可执行计划并清楚显示下一章准备状态 |
| R2 逐章生产 | R0、R1 | 正文、抽取、评审、局部返修 | 真实模型写完一章，作者可读、可修、可采用 |
| R3 评论与讨论 | R1、R2 | 评论改稿、想法讨论转计划 | 作者两句话即可发起改稿或完善未来剧情，所有结果经确认生效 |
| R4 修订与验收 | R0—R3 | 早章影响、阶段快照、P0 收尾 | 连续 10 章通过真实作者验收并完成故障、修订、导出回归 |
| R5 长篇强化 | P0 验收完成 | 小批自动、动态复盘、精准影响、旧稿导入 | 完成 20 章／一卷，长期状态一致，范围授权不越界 |

下面的 R0—R4 可分别提交 PR；不要把全部内容挤进一个不可审查的巨型改动。任务可以拆小，但不能打破版本、证据与采用边界。

- [ ] 记录 task stage、attempt、input fingerprint、模型产物、费用与租约令牌。
- [ ] 幂等请求复用同次结果；失败重新尝试生成新 attempt，不永久返回旧坏候选。

- [ ] 定义服务端必需检查注册表和 policyVersion，不允许客户端选择跳过。
- [ ] 缺失、unavailable、inconclusive 均阻断对应必需门槛。
- [ ] 引入不可变 ReviewRun／ReviewIssue，结果关联候选 hash 与输入版本。

## R2. 逐章正文、评审与局部返修（P0）

### DEV-13：真正可用的章节上下文

- [ ] 将实际事件值、人物与关系状态、资源、人物认知、相关历史原文加入 ContextPayload。
- [ ] 明确区分当前事实、作者约定、未来计划、候选参考，不使用过期事件。
- [ ] 写／改第 N 章以 N 章之前有效事实为准，后文只供独立影响分析，不当作角色知识。
- [ ] 保存本次真实 manifest 与 payload 或足以复现的不可变引用。
- [ ] 必需资料超预算停止／拆分，可选裁减记录到清单；不只传 eventIds。

相关位置：`contextManifestFor`、`packages/planner/`、application、persistence。
需求：WRITE-03/04/06、BASE-09。
验收：AT-12/13/43；第 5 章重要资源变化在第 20 章仍可见。

### DEV-14：事件合同、独立抽取与证据核验

- [ ] 为各事件类型明确 predicate、operation、value、单位、sequence 和 storyTime。
- [ ] 抽取调用不看 proposedEvents；每个关键事实有可定位正文证据。
- [ ] 统一实体别名与字段表示后比对，区分回忆、猜测、谎言和实际事件。
- [ ] 同章重复但不同顺序的事件不被错误去重；不把 JSON 对象键顺序误当作语义变化。
- [ ] 事件缺失或矛盾输出结构化问题，不直接强行对齐为一致。

### DEV-15：叙事评审、字数与人工裁决

- [ ] 检查任务落实、人物动机、因果、铺垫／兑现、重复与关键场景展开。
- [ ] 区分阻断与表达建议；所有问题都尽量有正文位置与理由，不只给一个分数。

- [ ] 作者可以拒绝表达建议或发起误报裁决；必需事实证据和硬规则不能直接跳过。

相关位置：core、planner、contracts、API、章节右侧评审面板。
需求：REVIEW-05/07/08。

### DEV-16：修订候选、差异预览与有限返修

- [ ] 修改创建新候选，原文不覆盖；手动编辑先保存草稿，提交时冻结候选。
- [ ] 默认最多两轮自动返修，超限进入作者处理；规划错误转为计划问题。
- [ ] 支持整次或部分采用补丁；部分采用后的组合稿重新抽取与检查。

- [ ] 保存中、已保存、未检查、阻断、待作者、已采用、待复核分别展示。

需求：UI-01—04、PRD 第 14 节。

## R3. 评论改稿与剧情讨论（P0，本轮重点新增）

### DEV-18：评论、回复和版本锚点

- [ ] 建立 thread/message，支持整章与选段、作者回复、状态筛选和历史版本查看。
- [ ] 保存 targetType、targetId、contentHash、quote、上下文和 Unicode code point 偏移。
- [ ] 验证选区引文与目标版本一致；新版不确定重定位时提示作者。
- [ ] 评论可重开，AI 不能自动关闭；旧评论不会因为新版本出现而丢失。

相关位置：contracts、core/comment 模块、persistence、API、章节编辑器选区菜单。
需求：COMMENT-01/02/07。
验收：AT-18/22；重复文本与 emoji 前缀的锚点测试通过。

### DEV-19：AI 回复与评论意图识别

- [ ] 区分解释提问、表达建议、当前剧情修改、未来期望和未定讨论。
- [ ] 提问先回答；意见含糊时陈述理解、建议行动与保持不变内容。
- [ ] 作者明确要求修改可直接生成预览，但不是直接正式采用。
- [ ] 重大剧情、早章因果、核心规则变化需先展示提案与影响。

相关位置：planner 中 discussion/revision 角色、application、评论 API 与侧栏。
需求：COMMENT-03/04、PRD 第 15.2 节。
验收：AT-16/17/40；“他为什么这样做”不会导致正文被自动替换。

### DEV-20：按评论修改与逐条验收

- [ ] 作者选择一条或多条评论，检查是否矛盾、重叠或触碰锁段。
- [ ] 创建 ChangeProposal，绑定选中评论和基线版本；复用 R2 修订生成能力。
- [ ] 差异展示每条评论是否处理、哪些未处理与原因。
- [ ] 提案 apply 只创建候选；重新检查并采用后进入评论待验收。
- [ ] 未选评论不执行；部分补丁接受创建新候选。

相关位置：application、contracts、persistence、评论面板、diff 面板。
需求：COMMENT-04—07、REVIEW-06。
验收：AT-17—22/25；能完成“评论→讨论→修改→复查→采用→作者关闭”。

### DEV-21：作者想法与多轮剧情讨论

- [ ] 多轮讨论显示作者原话、已确认要求、AI 建议和待决问题。
- [ ] 对话上下文绑定当时事实与计划版本；作者保存草记不必立即调用模型。
- [ ] 支持放弃方案、归档想法、继续讨论，保留历史。

相关位置：core/idea 模块、persistence、planner、API、剧情讨论侧栏。
需求：IDEA-01/02/03/07。
验收：AT-23；“妹妹后面黑化”不会马上改变当前人物状态。

### DEV-22：把讨论变成可批准的计划提案

- [ ] 从指定消息形成结构化 PlanChangeProposal，带 scope、ops、来源与 baseRefs。
- [ ] 展示对人物弧光、章纲、高潮、伏笔和前置条件的影响。
- [ ] 矛盾已采用事实时展示证据，要求调整方案或进入早章修订，不直接激活。
- [ ] 作者批准后原子创建并激活新计划；依赖旧版本的候选标为 stale。

相关位置：application proposal 用例、planning 模块、contracts、API、提案 diff。
需求：IDEA-04/05/06/07、PLAN-07。
验收：AT-24—26；计划批准不产生正式 StoryEvent。

## R4. 早章修订、阶段书稿与 P0 验收（P0）

### DEV-23：早章修订候选与后文影响预览

- [ ] 修订早章不立即停用旧正式链；先形成可读候选与影响报告。
- [ ] 报告变化事实、潜在依赖章节和未覆盖范围，第一版保守而不假装精确。
- [ ] 作者采用修订后，事务中停用后续事实、标记后文待复核、暂停运行。
- [ ] 目录和修订页保留所有历史版本与待复核状态。

相关位置：core、application、persistence、章节目录与修订页。
需求：EDIT-01/02/03。
验收：AT-27/28；修改预览不影响正式链，正式切换才影响。

### DEV-24：顺序复核并恢复有效后文

- [ ] 从最早待复核章开始，基于新事实与依赖重新检查。
- [ ] 正文不需变动时生成新的验证／候选依据，也不沿用旧检查。
- [ ] 需要修改时复用局部返修与作者确认。
- [ ] 恢复顺序与采用幂等一致，事件不重复入账；回滚早章也走同一影响流程。

相关位置：application、core、persistence、修订进度页。
需求：EDIT-04、BASE-06。
验收：AT-29/30；“待复核”不等于强迫重写全部后文。

### DEV-25：阶段快照和历史稳定导出

- [ ] 阶段冻结与全书完结分成两个入口及检查策略。
- [ ] 快照固定正文、约定、设计、计划、事件集合及来源引用。
- [ ] 导出历史快照不读当前 active 过滤，也不拿当前世界包替代历史版本。
- [ ] Markdown 仅输出正文；JSON 输出选定快照结构；评论与密钥默认不进入正文导出。

相关位置：finalize／export API、core Manuscript、persistence、ChaptersPage／成稿页。
需求：BOOK-01/02/03。
验收：AT-37—39；10 章可以阶段导出，100→450 后旧书稿保持不变。

### DEV-26：隐私、备份、错误提示和迁移

- [ ] 补密钥与模型日志脱敏；明确调用发送范围，不能把讨论全文无条件发给所有角色。
- [ ] 远程部署认证与作品作用域核验；选区／评论／提案不能引用其他作品资源。
- [ ] 项目导出备份与恢复演练，说明删除范围及第三方保留限制。
- [ ] 历史数据迁移保守处理缺失版本，不让旧候选伪装新候选；旧 locked 语义不自动放宽。
- [ ] 清理失效入口和误导文案，长任务可恢复，错误给明确下一步。

相关位置：API、model-gateway、persistence、前端公共错误处理、文档。
需求：BASE-08、UI-02/03/04。
验收：AT-40/42；跨作品非法引用、无效锚点、失败导出均有测试。

### DEV-27：全量回归与真实作品试写

- [ ] 跑 R0—R4 单元、持久仓储与 API 回归，核对 PRD AT-01—44。
- [ ] 使用真实模型完成至少 10 章，每章保留输入快照、候选、独立抽取、检查与采用记录。
- [ ] 至少执行一次评论局部修改、一次后续计划讨论、一次早章修订、一次服务恢复和一次历史快照导出。
- [ ] 作者抽样核查漏报与误报，记录采用后返工；不得让评审模型自己证明全部质量。
- [ ] 记录每千字采用稿成本、作者操作、失败次数和未覆盖范围；更新已知限制。

需求：所有 P0。
验收：AT-44 与全部 P0 回归；报告明确真实模型／伪模型、测试环境和提交，不写未经执行的“全部通过”。

**R4 出口：** P0 正式完成。阶段快照、评论、讨论、修订与恢复全部能够演示并有持久化记录。

## C. 测试数据建议

至少维护以下可重复夹具：

| 夹具 | 用途 |
| --- | --- |
| 50 条章纲、3 卷、主线和伏笔齐全的小型作品 | 计划范围、引用与任务前置 |
| 第 5 章耗尽遁符，第 20 章又要求使用 | 长期资源状态与上下文召回 |
| 第 12 章替换账册，主角第 23 章才发现 | 客观事实与人物认知隔离 |
| 一段正文出现两次同样句子，前面包含 emoji | 评论选区坐标、引用校验与失效锚点 |
| 已采用人物死亡，但讨论要求后续继续行动 | 未来提案与已发生事实冲突 |
| 两个 runId、同一幂等键不同请求、服务重启 | 并发、去重、恢复与过期提交 |
| 10 章阶段稿与后续改动后的同一项目 | 历史快照稳定导出与备份恢复 |

同一测试至少同时断言“应该发生的变化”和“不应该变化的对象”，例如改对话不能改变事件，批准计划不能改变正式正文。

## E. 产品交付时的一句话演示

“先看这本书的分卷和前 50 章计划，再准备第 1 章。写完后，我选一段评论‘这里不要让主角直接相信对方’，AI 给出局部修改和差异，我确认后采用。然后我随手记下‘第二卷希望妹妹逐渐转变’，与 AI 讨论并批准一个后续提案。它只更新未来计划，不改掉已经写成的故事。”

只要这个演示还需要绕过检查、手动改数据库或重新复制一大段上下文，核心流程就还没有完成。
