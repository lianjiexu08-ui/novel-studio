# 41条阻塞的分阶段验收义务

当前41条阻塞未改变。本次逐条人工指定应核的领域、章节范围与证据类型，并保留问题原文、来源文档、原文哈希及现有关联要求。不是按关键词自动分类，也不改变应用门禁。

41条记录按关联主题整理为28组；跨圣经和计划的同文记录仍分别保留，不能一条通过就自动关闭另一条。39条包含正文执行或历史替换义务；另外2条为同主题的评审容量/全量复审记录，主要需要当前版本的完整评审证据。

| 阶段 | 必需证据 | 不能代替它的材料 |
| --- | --- | --- |
| 设计 | 当前输入的相关正式评审、全部原始负面与人工争议核对 | 旧版本、局部报告、代码测试通过 |
| 章纲 | 对应区间的细纲与可验证执行要求，按窗口生成并复核 | 51–100宏观安排或未来450章容量算例 |
| 正文执行 | 实际采用版本、候选、原评审输入与引文一致，行动和状态可重建 | 草稿、任务卡、旧计划已通过正文 |
| 历史替换 | 旧文旧事件保留，新当前版本与事件一致，旧内容不再污染新账 | 删除失败记录、改写历史、混用新旧余额 |

v10草案的40项章节验收要求中，33项准确绑定到具体问题，分布于13条问题记录。其余28条记录当前没有直接关联的章节要求。这不证明它们缺设计，也不能据此猜测已由另一同主题要求覆盖。尤其是时间线、后半段信报、法宝流转、人物关系及宏观高潮，仍需在相应章纲展开时逐项落实。2条容量记录本身不需要勉强挂到某章正文。

所列章节范围只帮助定位，不宣称穷尽。首仓火的倾灯责任或携页者无法查明时，允许故事如实保留未查明边界；不能为关闭质量问题而编造破案证据。高阶资源容量算例也不能授予未来人物实际所得。

目前 `world.ts` 的审核、锁定与写作检查，以及 `planning.ts` 的计划审核，都将所有 `blocking && status !== 'resolved'` 视为前置阻塞。因此，即便后续四领域通过，也不能直接把这41条混合义务批量标为已解决。正式评审结束后，须依据逐项结果确定设计返修、阶段性规划、实际执行与历史替换各自的处理；若实现分阶段门禁，必须保留问题历史、明确的状态转换依据和后续未完成义务。**本次没有实施门禁变更，没有授权当前设计进入写作。**

生成器校验全部41条均被明确覆盖、无重复或漏项；清单列出的所有正文关联均直接读取v10的 `sourceQuestion`，不猜测主题关系。所有阶段均为待验收，自动关闭始终为否。
