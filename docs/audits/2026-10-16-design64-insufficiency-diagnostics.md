# 材料不足字段冲突的精确诊断

正式人物评审 `batch-5` 的首次回答在 `knowledge` 检查中同时填写 `awaitingSources` 与自由文本 `insufficiencyReason`。旧修正流程先收到枚举错误，模型把原因改成了合法枚举，却仍保留两个互斥字段，导致修正后再次失败。原两份回答及失败记录均已保留。

新增只读字段检查，在完整 schema 解析前汇总每个错误的检查下标、标准名和类型，区分非 insufficient 结论使用不足原因、原因与补读等待并存、原因值不合法。核心内容校验也使用相同诊断。模型修正提示明确说明两种处置的适用条件、应省略的字段以及不得用空值占位；保留一次有界修正，不自动删除字段，不替模型选择结论。

这不改变接受标准。完整 schema、请求编号、片段编号、证据、补读目录、必引材料及报告容量仍须校验。错误响应修正后若仍冲突，继续失败，并保留两次原始输出。其他检查的返修、普通不足和等待补读不能因修格式而自动通过。

新增4项回归检查覆盖：成功修正仍保留负面判断与完整补读列表、第二次仍冲突继续失败、多个检查的全部字段错误和 null 占位、诊断不能绕过请求绑定与完整 schema。隔离环境中35项设计评审测试通过；随后 `node scripts/test-all.mjs` 共516项通过，0失败。

对本次真实失败回答做离线诊断，首次准确定位 `knowledge` 的两类错误，第二次定位同项的字段冲突。同名 JSON 保存原响应哈希与诊断；未调用模型，也未把失败回答转换成成功报告。正式评审仍运行冻结版本，138个源文件哈希保持不变，此改动尚未部署到正式队列或其排队恢复器。
