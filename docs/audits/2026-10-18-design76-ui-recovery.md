# 第76版评审界面修复

## 已复现的问题

原本5180的旧前端仍在运行，但8787接口没有监听。先用第0段的已验证数据库副本恢复接口进行页面验收，发现设计历史、质量审计、评审列表的并发读取会报SQLite/Prisma事务等待超时。该副本没有写入者，因此不能把故障只归因于正式模型评审。

每个完整作品读取都会开启事务并分块加载历史。修复前，同一个Prisma客户端同时发起多个长事务，等待时间落在数据库的事务获取阶段；原有按作品的写入锁未覆盖读取。

## 修复与验证

- 按共享Prisma客户端排队执行仓库的读取、保存和事务；不同仓库实例共用该客户端时也遵守同一顺序。保留快照一致性、乐观版本检查、回滚与分块历史读写，每次读取仍返回独立作品对象。
- 外部已开启的事务客户端读取仍直接使用原事务，不再嵌套事务。
- 设计页面读取失败时明确显示错误和重试按钮，避免显示为空设定并提供生成入口。
- 持久化相关21项测试通过；仓库修复后全量611项测试通过。随后页面错误状态修改另经TypeScript检查、两份Vite构建及浏览器故障注入/重试验证。仅有已有的大包体积构建提醒。

副本页面真实请求已验证：作品、设计、版本历史、质量审计、评审摘要、世界批次3详情、独立核对记录及完整引用来源均返回成功。浏览器显示世界40、圣经72、计划76、批准计划10及原41项阻塞。人为注入一次设计读取503后，只显示错误与重试；点击重试恢复原设计，未发生任何写请求或模型调用。

“陆沉舟/陆沉川”说明已在副本验证：原模型评语与判定保留，说明作为独立记录显示，可打开第53章宏观安排的完整原文。副本验收不等于该说明已写入正式库。

证据：

## 边界

正式评审继续使用原冻结运行时，未覆盖其文件。新的界面后端单独冻结在`design76-ui-runtime-v2`；准备记录不是正式服务已恢复的证明。正式恢复须等当前评审段正常停止、核验落盘结果，再保存说明并启动8787与5180。

当前排队范围是同一个进程内共享Prisma客户端的仓库事务，不是跨进程数据库锁。完整历史加载仍较慢，本次没有通过缓存共享可变作品、删除旧报告或提高内存来掩盖问题。页面验收不批准设计、不关闭阻塞、不生成正文。

随后在独立临时SQLite库做了跨客户端复现：第一个客户端开启只读事务并保持6.5秒，Prisma实际发送`BEGIN IMMEDIATE`；第二个客户端开启读取，在5357毫秒后返回`P1008`。因此不能把同客户端修复声称为独立评审进程与接口可安全同时运行。正式接口恢复后，不应直接重启原冻结评审脚本并让两者同时访问正式库；下一段续审前须协调这两个入口，或验证新的单进程共享仓库执行方式。原冻结评审代码与既有证据不能为此直接覆盖。

## 慢查询自动刷新退避

前端已增加按实际读取耗时调整的自动刷新间隔：读取成功后至少等待15秒，并取本次耗时的3倍（最多120秒）；旧版无修订标记接口仍至少等待60秒。读取失败后等待60秒再自动重试，手动刷新和切回页面仍可立即尝试。该变更减少慢查询之间的自动重复读取，不解决后端整份历史加载的根本内存成本。

前端提交`394f766`通过类型检查、构建和12项现有前端测试。5180预览切换到单独的`data/audit-ui/design76-review/dist-v4`目录，保留原dist-v3不改；真实页面已显示四领域7步，刷新失败提示在恢复读取后清除。文件散列与页面证据见`2026-10-18-design76-adaptive-polling-ui.json`，未声称已测得吞吐或峰值内存改善。
