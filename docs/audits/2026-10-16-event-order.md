# 同章事件顺序与状态重建修复

发现：状态投影、写作上下文、正文评审和计划推进中，多处按“章节号 + 随机事件编号”取最后一条；JSON 的状态缓存与 SQLite 重载后的投影也可能不同。同章先得十枚灵石再花两枚，可能重建成余十枚。原独立提取校验使用集合，另会忽略变化顺序与重复次数。

修复使用章节版本的 `sourceCandidateId` 找到已采纳候选稿，核对作品、章节、采纳版本、正文及哈希、完整事件数量和内容，按保留的 `proposedEvents` 数组逐次恢复采纳顺序。对象键顺序及缺省证据按持久化语义处理，重复事件按出现次数配对，不合并 `A → B → A`。完全相同的多次记录无法恢复各随机 ID 对应的实际发生次序，使用确定性配对；其值与语义顺序不受影响，不声称恢复了物理插入顺序。

人物状态、认知、关系、资源/法宝状态、人物弧光、承诺、开放线、卷进度、计划推进、收束检查、写作/评审/规划上下文和章节状态 API 共用这一顺序。内容编辑继承原事件顺序；早章替换保留旧事件并使下游失效。JSON 重载从事件重建可丢弃的状态缓存。独立提取校验按同一对象/字段的变化序列比较，允许无关对象分组顺序不同，但拒绝状态变化倒序或漏掉重复次数。

旧记录缺少候选稿时保留确定性展示顺序。若同章同一状态发生不同变化、顺序不可证明，或已绑定候选稿与事件不一致，则明确列出 `eventOrderIssues`：阻止继续生成、采纳后章、继承不确定事件的内容编辑、正文评审、基于既有事实规划，以及最终收束验收。计划推进标为证据不足。界面质量页显示问题。旧记录的状态展示仍属临时重建结果，不能据此认定顺序或通过验收；需要通过明确的章节修订重新提取与评审，不自动改写历史。
