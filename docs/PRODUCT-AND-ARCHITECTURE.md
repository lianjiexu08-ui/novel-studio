# 自动小说创作与连载服务：产品与代码架构设计

版本：讨论稿 v0.4
日期：2026-10-09  
状态：设计提案。完整服务尚未实现；现有 worldforge-xuanhuan 目录是独立的离线页面原型。

## 1. 目标、已确定需求与待决事项

最终目标是将用户的创作意图转化为可持续更新的长篇小说，并支持投稿与连载发布。

已确定：
- 第一题材为玄幻，后续能够增加其他题材。
- 长篇连载；尽量自动完成规划、写作、检查、修订和存稿。
- 两种开书入口：用户提供创意后展开；用户选择题材与偏好，系统提供候选方案，由用户选中。
- 模型通过用户提供的 API 地址与 Key 调用。
- 平台与账号规则配置后，尽量自动投稿和更新。
- 运行环境按本地可运行、可迁移云端设计。
- 人物关系可以锁定；需处理人物弧光、群像分工、大纲连贯、节奏、时空与细节一致性。

当前设计建议：
- 个人使用优先，可管理多部作品；默认同一本书按章节顺序生成与采用。
- 默认由系统创建和维护设定、计划、审查及状态记录，用户可以检查、修改和锁定。
- 模块化单体业务核心，API 与后台工作进程分别运行。
- 自动修订在作者锁定约束内进行；无法解决的阻断问题暂停相关内容发布。

尚待决定：
- 第一个投稿平台及其实际可用的接入方式、稿件规则。
- API 的实际协议、模型能力、限流与调用限制；提供信息时无需在聊天里直接发送 Key。
- 每部作品的目标篇幅、单章字数、日更节奏、存稿目标、修订上限。
- 本地或云端的首次部署位置。此选择不改变核心业务模块。
- 未来是否面向其他作者提供服务；多用户商业平台不是本次已确认需求。

世界与人物页面的内部视图：
1. 世界规则：力量来源、门槛、代价、反制、资源与制度。
2. 人物档案：身份、目标、价值取向、知识与误信、当前状态、表达方式。
3. 人物关系：方向、类型、有效时间、锁定状态、事实与认知的区别。
4. 人物发展：计划中的弧光、正文中的关键选择、变化依据与缺口。
5. 群像分工：角色目标、本卷职责、独立行动、关键决定、预计收束位置。
6. 故事事实：时间线、位置、物品转移、能力变化及对应正文证据。
7. 文风与叙事约定：读者定位、人称视角、认可样段、反例与表达偏好；作为专属作品配置维护。

页面不要求用户手工录入所有数据。系统先提取与规划，用户仅在需要时检查或修改。

## 3. 创作流程

### 3.1 开书

创意输入或候选方案选择
→ 创作约定、读者定位与核心吸引点
→ 世界规则与人物
→ 全书目标、结局方向与分卷规划
→ 近期章节和场景计划
→ 两三章试写与文风校准
→ 自动写作。

样章可作为文风参考而不采用其剧情。仅正式采用的样章进入故事状态。用户可选择自行比较样章或交给系统初选；文风基准确定后无需逐章确认。

创作约定保存题材、叙事风格、读者体验目标、明确要求、避免元素、锁定关系与目标篇幅。自然语言要求转换为结构化约束时，需要展示解释和歧义；模型无法自动判断的要求保留为待明确项。

### 3.2 一章的生产流程

1. 读取当前采用版本、故事状态版本和约束版本。
2. 检查章节计划的前置条件与本卷剩余任务。
3. 组装上下文：场景相关人物、关系、知识范围、资源状态、相关原文、伏笔和文风要求。
4. 生成候选正文，保存为不可覆盖的新版本。
5. 从候选稿提取候选事件与状态变化。
6. 运行确定性检查和基于证据的语义审查。
7. 针对具体问题进行有限次数的修订，每次产生新版本。
8. 对修订后的实际文本重新检查，包括修改是否引入新问题。
9. 满足采用条件后，原子地保存采用版本、故事状态变化、证据与依赖。
10. 通过发布检查后进入合格存稿队列。

计划和事实分开保存。未来会发生的成长或揭秘，不能提前进入人物的当前状态与知情范围。

### 3.3 自动运行

- 每部作品配置单章字数区间、日更计划、合格存稿目标、允许的修订次数和调用上限。
- 调度器根据存稿缺口产生创作任务；达到目标后停止补稿，等待下一次需求。
- 同一本书的后续章节依赖前一章采用后的状态，默认顺序采用。
- 同一章的独立审查可以并行；不同作品可以受控并行。
- 暂停请求阻止新的步骤开始；正在等待的模型调用即使返回，也须在提交检查点前确认任务状态。
- 页面关闭不影响后台服务。运行在本地时，主机需要保持运行。
- 外部调用成功但本地未保存结果的情况，可能产生重复模型费用；记录每次尝试，不能承诺供应商侧恰好执行一次。

## 4. 一致性与文学质量机制

### 4.1 人物与关系

每个人物使用稳定 ID；姓名、化名与称号都绑定同一 ID。

关系分别记录：
- 世界中的客观关系；
- 人物的认知或误信；
- 对外身份与作者暂未揭示的事实；
- 关系方向、有效故事时间、来源与锁定级别。

已锁定事实只能经明确的设定变更操作修改，写作与事实提取模型没有直接修改权限。反向关系与称谓由明确规则派生，规则允许按题材和作品配置。

关系变化必须有采用正文中的事件依据。亲属身份、合作关系、情感倾向分别管理，避免把信任变化误写为身份变化。台词中的谎话或猜测不能直接成为世界事实。

### 4.2 人物弧光

记录初始信念、挑战事件、人物理解、关键选择、后果与后续表现。计划中的成长路径与正文实际达成的变化分开。

审查依据是角色做出的选择及其动机，不强制所有角色正向成长，也允许反复、退步与稳定型角色。

重要角色必须具有自己的目标、利益、拒绝条件和独立决定。工具人风险报告需要具体说明行动为何缺少角色自身的理由。

### 4.3 群像

角色可分核心人物、长期配角、阶段角色，但不用固定篇幅配额决定质量。

分卷计划记录谁承担关键选择、谁引发变化、谁承担后果；正文完成后核对实际分工。角色互换后仍不影响剧情、主角长期缺乏决定、重要配角无独立目标等情况产生有证据的疑点报告。

登场频次、连续缺席和视角篇幅仅用于发现异常，不能自动证明配角应被删除或主角必须增加戏份。

### 4.4 大纲

全书、分卷、章节三个层级分别保存目标与版本。每个关键节点具有：
- 要达成的结果；
- 前置事实或事件；
- 当前是否已兑现及正文依据；
- 后续依赖；
- 预计推进或收束区间。

保留全书核心目标，滚动细化近期章节。调整局部路径时检查作者锁定项与已发布事实。核心目标调整保留理由和影响范围，不能悄悄漂移。

支线记录用途、推进节点、与主线/人物/主题的联系、收束条件。系统能统计逾期和停滞；文学必要性由正文分析决定。

### 4.5 节奏

按卷和章节窗口对照篇幅消耗、信息变化、关系变化、情绪推进、局势转变及剩余任务。

提前发现开局长期未进入有效冲突、重复场景未带来新结果、结尾剩余篇幅无法承载收束等问题。铺垫、日常与低强度章节允许存在，审查需结合它们的作用及后续兑现情况。

不以每章战斗数、反转数或统一质量分决定发布。

### 4.6 时间、空间与物品

同时记录叙述顺序与故事发生时间。故事时间可以是明确日期、相对顺序或区间，未知时间保持未知。

年龄、唯一物品重复占有等明确约束用程序检查；旅行是否合理、超自然能力是否允许等问题结合世界规则审查。物品转移、受伤与恢复、境界变化、角色获知信息均关联事件和原文版本。

### 4.7 检索与证据

先按人物 ID、关系、事件时间、计划依赖和章节版本获取必须带入的信息，再补充检索到的相关内容。摘要用于定位，存在冲突时回到原文证据。

语义检索可以作为辅助能力，不承担唯一的事实来源。确定性校验只能严格验证已结构化且可靠的事实，抽取本身仍可能出错，因此冲突修复必须复核原文。

## 5. 版本、状态与变更影响

至少区分四类内容：
- 候选稿：创作与修订的尝试，不进入正式故事状态。
- 采用稿：当前被作品接受的正文版本，能产生带证据的故事状态。
- 合格存稿：采用稿的检查结果对当前内容、约束和状态版本仍然有效，没有未解决的阻断问题。
- 发布快照：准备提交或已提交平台的精确内容与校验值，发布后保留历史记录。

采用后再编辑正文，应创建新的候选版本；旧采用版本继续保留，直到新版本被正式采用。

采用事务同时完成：
1. 校验输入的约束、计划与故事状态版本未过期；
2. 保存采用版本指针；
3. 保存事件、人物与资源等状态变化及证据；
4. 保存变更依赖和审查结果；
5. 写入后续任务通知记录。

早期章节、关系或世界规则变化后：
- 根据事实引用与依赖查找受影响的计划、后文和报告；
- 将其标为待重新验证；
- 暂停受影响版本的发布；
- 对未发布内容执行必要修订；
- 已发布内容保留快照，通过单独的修订任务管理；
- 通过再次检查后恢复推进。

依赖关系可能漏抽。对于无法准确限定的重大变更，扩大到后续章节范围进行复核，不能把没有记录依赖当成没有影响。

## 6. 审查与发布条件

每条问题保存：
- 类型与检查来源；
- 阻断、警告或建议；
- 确定冲突、语义疑点或信息不足；
- 人物、物品、事件、计划等关联 ID；
- 原文版本与段落证据；
- 建议修复方式；
- 当前处理状态；
- 检查所依据的约束版本与故事状态版本。

规则检查与模型审查分开记录。多个模型意见一致不等于事实正确，意见冲突时回到证据。

“检查通过”只表示当前版本满足已配置检查条件，不表示文学质量或所有逻辑问题都得到绝对保证。

发布检查至少确认：
- 内容版本与已通过检查的版本一致；
- 相关约束、前置章节与故事状态没有使检查结果失效；
- 无未解决的阻断问题；
- 章节编号、标题与目标平台作品对应正确；
- 发布时间符合计划；
- 平台连接状态有效；
- 该发布意图没有已确认成功的重复记录。

## 7. 投稿与连载

投稿与日常更新分开管理：
- 投稿：简介、标签、作者资料引用、首批稿件、目标平台、提交结果与平台作品 ID。
- 更新：章节发布快照、计划时间、顺序、提交尝试、核验结果与平台章节 ID。

平台适配器应声明能力：
- 是否能够创建作品或提交投稿材料；
- 是否能够发布章节；
- 是否支持查询发布结果；
- 是否允许编辑已发布章节；
- 支持哪些认证与内容格式。

只有选定平台并核实其现行规则与实际接入能力后，才能承诺该平台的自动化范围。没有通用接口的假设；网页自动化也需要先验证适用性与稳定性。

发布任务采用稳定的发布意图 ID，同一章节的正常首发与之后明确发起的修订分别记录。提交超时或连接中断后，状态为未知，先核验平台结果，再决定是否重试。应用侧去重不能保证不受控平台的恰好一次执行。

状态示例：
scheduled → submitting → verifying → published
                         ↘ unknown → verifying
                         ↘ failed / blocked

账号失效、平台拒稿或需要在平台处理的问题进入可恢复状态并说明原因。

## 8. 技术架构建议

推荐统一使用 TypeScript，采用模块化单体业务核心与独立后台进程：

| 层 | 建议技术 | 职责 |
| --- | --- | --- |
| 浏览器界面 | React + Vite + TypeScript | 工作台、编辑、关系与时间线、任务与问题操作 |
| HTTP 服务 | NestJS | 身份与配置、查询、操作入口、SSE 进度推送 |
| 后台进程 | Node.js 工作进程 + BullMQ | 长任务、调度、限流、重试、检查点与恢复 |
| 业务数据库 | PostgreSQL + Prisma | 作品、不可变版本、故事事实、计划、任务与发布记录 |
| 队列基础设施 | Redis | 任务投递与运行协调 |
| 结构化契约 | Zod / JSON Schema | 前后端契约、模型输出校验、工具调用参数边界 |
| 本地部署 | Docker Compose | API、工作进程、数据库、Redis 与持久化卷 |

PostgreSQL 是业务状态的依据；Redis 队列不能成为唯一任务记录。数据库事务写入任务通知，分发器再投递队列，配合定期对账恢复未投递或中断的任务。

人物关系先由关系表与关联查询保存，页面可呈现为图。检索优先使用明确实体与证据关系，后续按需要增加语义检索。

题材使用 GenreProfile 配置：定义可选字段、默认规则、规划模板、写作偏好与专用审查策略。第一份配置为玄幻；之后增加题材时复用作品、版本、任务和发布流程。作品中明确修改或锁定的设定优先于题材默认值。

默认本地部署绑定本机访问；迁云时启用访问认证、TLS、密钥配置与备份策略。API Key 保存在服务端并加密，前端只显示脱敏信息，调用日志不记录完整密钥。

- web 依赖共享契约，通过 API 访问服务。
- api 与 worker 调用 core 的同一组业务用例。
- core 声明存储、模型与平台能力接口，不依赖具体供应商或网页结构。
- persistence、model-gateway、platform-adapters 实现这些接口。
- apps 的启动层负责装配实现。
- 提示词有版本，任务记录所用版本；核心约束在程序与数据库层执行。

| 领域 | 主要对象 |

| 人物与世界 | Character、Alias、WorldRule、Relationship、ArcPlan、CastRole |
| 大纲 | OutlineRevision、Volume、PlotNode、Dependency、Subplot、Foreshadow |

所有业务查询按作品隔离。证据引用不可变的正文版本和段落位置；故事发生时间与数据库写入时间分别保存。

关系、世界规则和计划均具有版本与有效范围。推断、猜测、暂定想法、作者真相与已采用事件具有不同状态，不能混入同一无标记文本库。

## 11. 模型调用

按任务角色配置模型：策划、正文、审稿、事实提取可以分别选择，也可使用同一供应商。

统一接口处理：
- 供应商协议与模型能力；
- 文本、结构化输出与流式响应；
- 结构校验与有限重试；
- 超时、并发和速率限制；
- 每次尝试的输入版本、模型参数、模板版本、耗时及用量；
- 长任务取消与检查点；
- 日志中的密钥与敏感信息脱敏。

不同 API 或中转服务的能力以实际探测和文档为准。模型返回的结构化数据先校验，再作为候选变更；不能由模型直接覆盖数据库中的锁定事实或执行发布。

## 12. 任务可靠性

任务步骤状态：
queued → running → succeeded
              ↘ retrying / failed
              ↘ pause_requested → paused
              ↘ stale / cancelled

每一步保存输入内容版本、约束版本、上下文摘要引用、输出、状态、尝试次数和检查点。

采用稿提交时检查故事状态版本。若在模型调用期间用户已修改设定或前文，当前结果标为需要重新验证，不能直接覆盖新状态。

恢复任务时：
- 已成功且版本仍有效的纯内部步骤可以复用结果；
- 过期步骤重新执行必要检查；
- 模型调用的重复尝试分别计费记录；
- 发布等外部副作用先核验结果，再决定动作。

同一作品默认限制并行写作链，跨作品并发受全局模型额度与服务容量约束。

## 13. 验收与实施顺序

验收至少包含：
1. 两种开书入口进入统一作品流程。
2. 锁定关系不能被生成或抽取任务覆盖。
3. 人物不会因未来弧光计划而提前改变当前状态。
4. 候选稿中的死亡、物品转移等不会污染采用稿事实。
5. 人物知情时间、身份称谓、物品归属等冲突有原文证据。
6. 大纲前置条件缺失能够在后续节点执行前发现。
7. 节奏与群像报告给出具体原因，允许有效铺垫和不同类型的角色发展。
8. 修改早章后，受影响后文与审查结果失效，相关发布受到阻止。
9. 中断或重启后恢复任务，不覆盖较新的设定和正文。
10. 发布超时不会触发无核验的重复提交。
11. 本地备份可恢复至另一环境，作品版本与事实依据保持完整。
12. 模型审查需评估漏报、误报和修复引入新问题，不能只测试输出字段齐全。
13. 认可样章的文风不会自动采用样章剧情；已采用的样章不会重复生成相同开篇。
14. 精确修改不得超出授权范围或覆盖锁段；版本过期时不能静默覆盖。
15. 模型升级使用固定场景评估，按作品显式记录配置版本和回退范围。
16. 阅读反馈保留来源与观察区间，不能直接写入事实、正文或发布计划。

建议实施顺序：
- 阶段一：确认第一个投稿平台的接入可行性；搭建作品、模型、版本和任务基础。
- 阶段二：贯通开书、人物关系、分层大纲、候选稿与采用稿流程。
- 阶段三：加入证据检索、事实检查、弧光与群像审查、局部修订及变更影响追踪。
- 阶段四：用连续章节场景验证自动存稿、恢复、节奏与长程一致性。
- 阶段五：接入首个平台的投稿与发布核验，完成端到端验收。
- 阶段六：根据实际创作反馈改进，再增加题材和平台适配器。

测试建议：领域规则与流程使用单元测试；采用事务、并发与恢复使用真实数据库集成测试；页面使用浏览器端到端测试；模型与平台先使用可控替身测试错误路径，再验证实际接入。

## 14. 能力边界

系统可以强制执行权限、版本、任务状态和明确的数据约束；正文事实抽取、人物动机、节奏和文学质量包含语义判断，不能承诺完全无错。

自动化范围受目标平台实际能力影响。当前尚未选定平台，不能把通用的自动投稿与定时发布视为已经可用的功能。

第一版目标是完整、可恢复、可检查的个人创作闭环。扩展题材、模型与平台通过模块接口完成，保持作品数据、版本和任务流程的一致性。

## 17. 开源对照后的收敛调整

本轮固定版本源码阅读记录见 OPEN-SOURCE-REVIEW.md。它没有改变本服务采用 Web/API/worker、PostgreSQL 和可迁云端的方向，而是把以下内容从原则变成实现契约：

- ContextManifest：记录本章实际使用的约束、正文、计划、人物状态、风格参考、版本、纳入原因、省略理由和容量状态。必需材料不足返回 needs_split 或 blocked。
- PlanRealization：绑定剧情节点、目标场景、采用正文版本、证据范围和落实状态。计划不会直接写入故事事实。
- StateProvenance：为人物位置、能力、伤势、物品和知识等字段保存来源、故事时间、有效性和失效原因。
- Obligation：记录玄幻中的誓约、承诺、交易条件和截止期限，包含触发条件、后果与证据。
- ChangeSet：把模型声明的变化与独立正文抽取的变化比对；没有正文证据的声明不入账，正文发生但声明遗漏会阻止采用。
- CheckExecution：每项必需检查记录 passed / failed / inconclusive / unavailable / not_applicable。必需检查未完成不能获得可发布资格。
- ProjectionTask：正文和已验证状态先在事务中采用；摘要、检索索引和导出由可重试的 outbox 任务派生。派生失败不重复采用正文，也不能让过期投影进入续写上下文。

页面不增加“上下文”“图谱”“伏笔”等独立顶级入口。作品内导航收敛为：概览、创作、设定、大纲、质量、发布。章节工作台侧栏显示本章依据、计划落实、审查、修订和任务；质量中心显示检查覆盖与依赖失效；任务中心显示可恢复候选与派生任务。

借鉴开源实现只表示机制已在公开源码中出现，不表示其长篇质量、自动发布或恢复能力已验证。四个项目的固定提交、代码链接、许可证边界和不应照搬的实现写在 OPEN-SOURCE-REVIEW.md；没有复制第三方代码。

本地 Spike 已验证第一条状态链：假模型连续采用 12 章、候选事件隔离、检查器 unavailable 阻止采用、早章修改停用受影响事件并重建状态、Python checkpoint 恢复幂等；Node 持久队列还验证了租约恢复、同作品串行、跨作品并行和任务去重。Spike 不是生产实现：Python 聚合仍在内存，Node JSON 文件只演示崩溃边界，尚未接入真实模型、PostgreSQL、Redis 或投稿平台。生产数据模型还应明确区分“最新历史版本”和“当前有效版本”，避免受早章修改影响的 stale 版本继续进入续写上下文。

## 15. 校准、编辑、评测与反馈补充

详细页面交互、默认决策和验收案例见 INTERACTION-AND-ACCEPTANCE.md。

### 15.1 文风校准

每部作品保存目标读者、核心吸引点、开篇承诺、人称视角、信息披露边界、语言与描写偏好，以及认可样段和反例。样章的正文版本、文风认可和剧情采用是不同记录。

系统初选样章不能被描述为用户已认可。后续每章绑定具体文风基准版本，系统在用户预先设定的自动化权限内运行。

### 15.2 编辑控制

修改请求记录所针对的正文版本、选中段落、期望目标、必须保留的事件与表达、锁定范围。锁定文本以不可变段落 ID 和内容校验值校验；未授权范围也校验是否发生变化。

模型的输出先形成候选补丁，经范围校验、锁段校验、事实检查后再采用。无法在允许范围内修复的冲突只暂停受影响内容，系统没有自行解除作者锁定的权限。

### 15.3 配置升级评测

模型、参数、提示词和工具能力组成可版本化配置。升级先在固定故事场景上比较约束遵循、对白与文风、抽取准确性、审查漏报误报、修复结果和调用消耗。

评估结果保留证据与不确定项，不用单一模型分数判定整体质量。任务绑定配置版本；已经开始的任务继续使用原版本或由用户显式取消重跑。配置回退只影响指定的后续任务，已产生正文如需修订必须单独执行。

### 15.4 反馈与经营观察

初期支持手工记录试读意见和平台指标。指标具有来源、定义、观察时间、覆盖区间与缺失状态，不把未知数据当作零。

反馈先形成可验证的观察，再形成有影响范围的改进建议。只有被允许的内容修改才能通过正常编辑流程执行；锁定关系、创作约定和事实变更仍受原有权限限制。读者评论不是写作执行指令，也不能直接触发投稿发布。

## 16. 第一阶段交付定义

第一阶段建议交付可持续运行的单人服务：
- 两种开书入口及玄幻题材配置。
- 样章校准、人物与世界规则、分层大纲和完整版本管理。
- 连续生成、审查、有限返修、采用、状态同步和存稿管理。
- 精确编辑、段落锁定、变更影响检查。
- 任务暂停恢复与调用记录。
- 第一个经验证可接入的平台的投稿和发布核验。
- 轻量配置评测、手工阅读反馈、备份迁移。

后续再扩展题材、平台、自动指标同步与更复杂的群像可视化。多用户收费、社区、模型训练、全平台自动运营暂不纳入第一阶段。

第一轮验证用连续 10—20 章观察实际可读性与流程稳定性，并用跨卷历史案例检查长期依赖。短程通过不能视为已经证明百万字的一致性。
